Chapter 01

A game you can explain

Start with behavior. Follow the state. Then name the pattern.

Survival Chaos began as a university game-jam project at PUC in 2023. A team made a playable orbital shooter under the constraints of a jam. Ian later rebuilt it in Unity 6.6 and HDRP 17.6. The valuable story is the sequence of decisions: discovering what the game actually did, preserving the parts that worked, and changing the structures that made mistakes easy.

You do not need to understand every file before you can understand the game. Start with a visible event: an enemy is hit. Find the method that receives it. Ask which value changes, who owns that value, and what happens next. Repeat that process until the event reaches something you can see or hear.

This book takes that route. It introduces the vocabulary beside the code that gives it meaning. The original Rebuild Reference is the source for the development history; the embedded C# excerpts are copied from this checkout. Historical anecdotes are identified as such. Live Inspector assignments and player-build behavior were not measured for this edition.

Objects & state→One hit→One reward→Boundaries→Movement→Presentation→Evidence

How to use this edition

Read the explanation, open its source excerpt, then answer the prediction question before revealing the answer. The final question in each chapter is a prompt for speaking about your project. It is not a script to memorize. A useful answer names a concrete problem, explains the choice, and admits what the evidence does not establish.

The interactive examples are small JavaScript teaching models. They do not run Unity, inspect the scene, or test the C# assembly. Values identified as exercise values belong to the demonstration; project values are identified by their source.

Keep the history, label the time

The old game had defects that the current code prevents. An old bug is evidence about an earlier implementation, not proof that it remains present. Conversely, a source comment can survive the implementation it describes. Read executable behavior and its surrounding context together.

Explain it in an interviewChoose one change you understand. Explain the original behavior, the reason for changing it, and how you would establish that the change succeeded.

Chapter 02

What an enemy actually is

Classes describe behavior; instances carry state.

A class defines a type: the fields it can hold and the methods that operate on them. An instance is a particular object of that type. Two instances can run the same method and contain different values. Sharing an enemy script does not force every enemy to share its current health.

In Unity, a GameObject is a container for components. A component derived from MonoBehaviour participates in Unity's lifecycle. A prefab stores a reusable object configuration. A spawned object is a runtime instance of that configuration. None of these is interchangeable with the C# source file that defines the component type.

Survival Chaos separates enemy configuration from an enemy's current condition. EnemyDefinition is a ScriptableObject with fields such as maximum health and experience reward. An Enemy can reference that definition. When enabled, it constructs a separate HealthState initialized from the definition's maximum health, falling back to its serialized field when no definition is assigned.

Current health changes here

A reference lets an object access another object. Copying the reference is not copying the referenced object. If several enemies reference the same definition, they can read the same configuration. Their separately constructed health objects still change independently.

[SerializeField] and private answer different questions. The attribute makes an eligible field part of Unity's stored configuration; the access modifier limits which C# code can access it directly. A read-only property such as MaxHealth lets other code inspect the value without exposing a public setter. These are tools for controlling how state is changed, called encapsulation.

The historical migration moved rewards out of hardcoded behavior and into definitions. Making a serialized per-prefab reward field would also have been possible. The definition groups related configuration and permits several prefabs to refer to the same authored data. Its cost is another asset and another reference that must be correct.

Show the reasoning

No. Each activation constructs its own HealthState. The definition supplies an initial number; it is not used as a shared current-health counter. If current health were stored in and written to the shared definition instead, that would be a different ownership model with different consequences.

Chapter 03

A hit is a change, not just a number

Learn fields, methods, return values, and invariants from HealthState.

HealthState is an ordinary C# class. It does not need a GameObject to exist. Its constructor establishes a starting condition: maximum health is at least one and current health begins at that maximum. A constructor prepares an instance when code creates it with new.

Its important rule is not merely “subtract damage.” The caller also needs to know whether this call caused a death. Otherwise, another hit on an already-dead enemy could award a second reward. The killReported field remembers whether that transition has already been reported.

Read TakeDamage in order. The first guard returns false if a kill was already reported. The subtraction treats negative damage as zero. If health remains positive, the method returns false. Otherwise, it records the death and returns true. Here, true means “the death transition happened now,” not “the object is dead.” Those are different questions.

A rule that must stay true across allowed operations is an invariant. The relevant invariant is that a HealthState reports its kill at most once. Notice what the method does not promise: it does not clamp current health to zero after overkill, and it does not create explosions or award experience. Those are callers' responsibilities.

Try the rule · teaching model

Start at 7 HP, taken from the existing StartsAtFullHealth test fixture—not an enemy balance setting.

Predict the return value before applying damage.

public bool TakeDamage(int amount)
{
    if (killReported)
    {
        return false;
    }

    current -= Mathf.Max(0, amount);

    if (!IsDead)
    {
        return false;
    }

    killReported = true;
    return true;
}

Stop & predict

Why not award experience whenever IsDead is true?

Show the reasoning

IsDead describes a state that remains true after death. A later callback can observe it again. TakeDamage’s return value identifies the single transition, so a caller that gates its reward on that result does not repeat the reward through that path. This is not a guarantee against unrelated code awarding experience twice.

Testable does not mean pure

HealthState changes its fields, so TakeDamage is not a pure function. A pure function returns a result from its inputs without modifying external state. This class is easy to test because its state and operations can be exercised directly, with no scene setup. It still uses UnityEngine.Mathf.

Explain it in an interviewExplain the difference between “is dead” and “was killed by this operation.” Where else would that distinction matter?

Chapter 04

Follow one shot through the game

An execution path connects the systems better than a list of filenames.

Consider the normal Enemy component receiving a trigger callback from a player projectile. This walkthrough covers that implementation, not every enemy or boss damage path. The projectile must satisfy the code's tag check; the actual physics configuration must also deliver the callback.

Walk the fatal-hit path

On a fatal hit, the enemy creates the explosion, calls its death handling, then despawns itself. Inside that death handling, EXP.AddEXP invokes the registered handlers. This C# event invocation is synchronous: the handlers run as part of that call before it returns. It is not a message waiting in an automatically created background queue.

The player's handler adds experience and checks its threshold. In the inspected implementation, reaching the threshold calls LevelUp, which resets current experience to zero. There is no loop carrying surplus experience through multiple levels in this method. That is the behavior to explain, even if a different progression system might preserve overflow.

The upgrade itself is separated in time. Preparing an offer does not apply every skill on it. The player must later collect a pickup through the normal pickup path. Learning to distinguish immediate calls from later interactions is essential when debugging event-driven games.

When a visible result fails, trace the boundary where the expected work stops. No experience could mean the death path did not run, the experience object was unavailable, or the handler was not subscribed. Reading only the health subtraction cannot settle all three. Ask for evidence at each boundary rather than adding fixes everywhere.

Chapter 05

Ask for a capability

An interface creates a contract; it does not provide the implementation.

An interface declares operations a caller may use. ISkillTarget includes operations such as healing, increasing maximum health, and increasing attack speed. Player implements that contract. A skill can receive an ISkillTarget without depending on all the other things Player knows about.

The attack-speed skill makes one request: target.IncreaseAttackSpeed(). It does not calculate the player's firing interval. A variable typed as the interface limits what the caller can ask for through that variable; the actual object's implementation determines what the call does. This ability to use different implementations through the same contract is polymorphism.

A test can supply a substitute that records the request. This is a small example of dependency injection: the dependency is supplied to the operation rather than discovered or constructed inside it. It does not require a framework or a container. Testing the skill's request does not prove that the real player's firing schedule changes correctly; that is another responsibility.

The input system illustrates a related boundary. Gameplay reads GameInput; its current IGameInput implementation supplies the values. The historical rebuild established that boundary before replacing the backend. A fake input source in the tests makes a key value available without pressing a physical key.

There is a cost: GameInput is a global access point, so a reader must look elsewhere to discover which source is installed. Tests that replace it must restore it. The setter's null fallback makes restoration convenient; the TearDown method is what actually performs that cleanup. An abstraction reduces one kind of coupling while introducing a boundary you must navigate.

Chapter 06

Who is still listening?

Events, pooling, scene changes, and static state all depend on lifetime.

An event lets a publisher announce something without directly naming every listener. VictoryMenu subscribes to RunOutcome.BossDefeated in OnEnable and unsubscribes in OnDisable. The boss can report the outcome while the UI decides how to display it.

This is a design choice, not a rule that spawned objects cannot access the scene. A spawner could supply a scene reference after instantiation. Here, event notification avoids making the boss responsible for finding a particular menu. In exchange, the subscription must exist when the event is raised.

Do not learn “nothing runs on an inactive object.” Ordinary C# method calls through a reference can still execute. Unity does not run Update on an inactive GameObject, and a listener that remains inactive does not subscribe via OnEnable. Deactivating a previously active component can invoke OnDisable. Callback scheduling and ordinary method calls are different mechanisms.

Pooling extends an instance's life

Returning an enemy to a pool does not reconstruct it. Fields can retain the state of its previous use. In this project's Enemy, Awake obtains the hit-flash component, while OnEnable creates fresh health. Another use needs preparation; it does not receive a fresh Awake and Start every time.

Create→Enable / prepare→Use→Disable / clean up→Enable again

Pending firing schedules and reused movement direction also need attention. The historical pooling fixes exist because an instance's retained state can be correct C# and wrong gameplay. Returning an object is an ownership decision: the pool may reuse it, so other systems must stop treating that activation as live.

A new scene is not a new static world

Static fields belong to the type rather than an individual scene object. The project resets relevant state at play-mode initialization and scene transitions. Those are different events. In RunOutcome, the scene-loaded hook clears the run-ended flag but deliberately preserves new subscriptions: the new scene's OnEnable callbacks have already registered them.

Chapter 07

The arena is an angle problem

Use units to derive movement instead of memorizing a formula.

The game looks three-dimensional, but much of its movement can be described by a bearing around a vertical axis, a distance from that axis, and a height. ArenaGeometry.OrbitRadius is documented as 137.2 units in the supplied guide. That radius is a project value; the calculations below are derived from it.

A radian connects an angle to arc distance: arc distance = radius × angle in radians. Therefore linear speed divided by radius gives radians per second. Multiplying by Mathf.Rad2Deg gives degrees per second. Finally, multiplying by Time.deltaTime gives the angle to apply during one update. RotateAround accepts that angle, not a speed.

units/second ÷ units → radians/second → degrees/second
degrees/second × seconds → degrees this update

Explore bearing · top-down schematic

The radius is the guide's 137.2 units. The speed starts at its documented 80°/s projectile example. Changes here are hypothetical, not tuning recommendations.

The sign convention matters. A positive Unity yaw around Vector3.up carries +X toward −Z. A textbook circle using a positive sine for Z travels the other way. The project uses quaternion rotation of Vector3.right where that bearing convention is needed. The schematic places +Z at the top, so positive yaw appears clockwise.

The camera and ship need matching angular movement. The inspected PlayerMovement converts using the arena lane radius, not each object's own radius. Otherwise, equal linear speeds on different radii would produce unequal angular speeds and a growing relative bearing. The camera is not an ordinary chase camera in this design.

Also distinguish distance across the ring from distance around it. Opposite points are a diameter apart in a straight line, and a half-circumference apart along the orbit. A proximity check can be wrong even with the right radius if you assume it measures the other distance.

void Update()
{
    if (center == null)
    {
        return;
    }

    float h = EffectiveHorizontal;
    float v = EffectiveVertical;

    Vector3 pos = center.position;
    pos.y = transform.position.y;

    // Authored in units per second, converted here to the angle RotateAround
    // actually wants. The conversion divides by the lane's radius rather than
    // by this object's own distance from the axis, and that distinction is
    // load-bearing: the Main Camera orbits 75 units further out, so measuring
    // against its own radius would hand it a smaller angle than the ship and
    // leave it trailing a little further behind every second.
    //
    // Read the other way round, the number means what it says for the ship -
    // which is on the lane - and means "keeps station with the ship" for
    // everything else running this.
    float degreesPerSecond = orbitSpeed * Mathf.Rad2Deg / ArenaGeometry.OrbitRadius;

    // Both axes take the dash, so the two authored speeds keep their
    // relationship through a burst the same way they keep it through a
    // run of speed picks - a dash that only moved you around the ring
    // would be no use against an attack that owns a height.
    float scale = speedMultiplier * dashMultiplier;

    transform.RotateAround(
        pos, Vector3.up, -h * Time.deltaTime * degreesPerSecond * scale);
    transform.LookAt(pos);

    transform.position += Vector3.up * v * Time.deltaTime * climbSpeed * scale;
}

Stop & predict

At the same angular speed, does a larger orbit cover more ground per second?

Show the reasoning

Yes. Linear speed is radius times angular speed in radians per second. The angle can remain equal while the arc distance grows. That is why “same speed” is incomplete until you specify angular or linear speed.

Chapter 08

Time is an input

Movement, smoothing, spawning, and pause ask different questions about time.

A frame is not a fixed duration. Multiplying a rate by elapsed time converts it to an amount for that update. That fixes a basic units mistake, but it does not automatically make every algorithm behave identically at every frame rate.

Lerp(a, b, t) interpolates between two values. When you repeatedly interpolate from the current value toward a target, you remove a fraction of the remaining error. Using response × deltaTime as that fraction is an approximation. For a fixed target, an exponential remaining-error factor composes consistently over time: exp(−k·a) × exp(−k·b) = exp(−k·(a+b)). That is why ShipMotion uses 1 - exp(-response * deltaTime) as the interpolation factor.

This is a property for the same fixed target and positive response. A target sampled differently during movement can still produce different trajectories. The helper also has an explicit project convention: a nonpositive response snaps to the target. That is a chosen branch, not a property of exponential decay.

Scheduling is different from integrating movement

WaveDirector runs a coroutine for each stream. A coroutine can yield and resume later; it is not automatically a background thread. Its normal C# work runs on Unity's main thread. The stream waits, spawns, computes an interval, and waits again. WaitForSeconds uses scaled time, so pause affects the wait.

SpawnMath calculates the interval from elapsed time: count completed ramp steps, raise the interval scale to that count, multiply by the base interval, and enforce a floor. A smaller interval means more frequent spawns. Computing from inputs lets you ask about a later time without simulating every previous wait. The caller still imposes scheduling limits, so formula output and exact spawn times are different claims.

Requested time and effective time

RunTime preserves a requested simulation speed while deriving the effective time scale from pause and run-end state. SettingsStore uses unscaled time for its save delay, so pausing gameplay does not prevent settings from reaching disk. Always ask which clock expresses the intended behavior.

public static float Approach(float current, float target, float response, float deltaTime)
{
    if (response <= 0f)
    {
        return target;
    }

    if (deltaTime <= 0f)
    {
        return current;
    }

    return Mathf.Lerp(current, target, 1f - Mathf.Exp(-response * deltaTime));
}

Chapter 09

An offer is not a purchase

Collections, randomness, and state transitions meet in the upgrade system.

A level-up offers alternatives. It does not mean every displayed skill has been taken. SkillPool separates Draw, which produces distinct candidates, from RecordPick, which charges an accepted pick against the limit. The historical bug this prevents is consuming a limited upgrade merely by showing it.

The pool uses a List to keep the skills it knows and a Dictionary to associate each definition with its pick count. A dictionary is a lookup from a key to a value. Here, the key is a definition object, not its displayed name. That distinction matters if two assets have similar names.

Draw copies the available candidates into a local list and removes each selected entry from that list. Removal prevents duplicates within that offer. It does not remove the definition from the master collection, and it does not record a pick. The copy holds references to the same definitions; it is not cloning the assets.

The constructor accepts a Func<int, int>: a callable that receives the available count and returns a selected index. Production defaults to Unity randomness; tests can supply a deterministic selector. The test controls the uncertain input so a failure can be reproduced. That is another small dependency-injection example.

SkillOffer groups the pickups belonging to one decision. Collecting a member forfeits its alternatives. Other offers remain independent. This separation resembles preparing a choice and committing it later, but the code is not a database transaction system. Draw filtering alone does not prove that a skill remains available when an older offer is collected. That is a separate question for the collection path; do not infer a reservation or revalidation guarantee from this method.

Rate and interval are reciprocals

The player's attack-speed implementation increases a rate multiplier, then divides the starting interval by it. This makes each pick add the same share of the starting rate until a safety floor applies. Repeatedly shrinking an interval is a different curve. Smaller absolute interval reductions do not by themselves mean smaller gains in shots per second—convert through the reciprocal before comparing.

public List<SkillDefinition> Draw(int count)
{
    var drawn = new List<SkillDefinition>();

    if (count < 1)
    {
        return drawn;
    }

    // A copy, because entries are removed as they are drawn to keep the
    // set distinct - and the shared buffer is refreshed from the pool
    // rather than owned by this call.
    RefreshAvailable();
    var remaining = new List<SkillDefinition>(availableBuffer);

    while (drawn.Count < count && remaining.Count > 0)
    {
        drawn.Add(TakeOne(remaining, refresh: false));

}

Chapter 10

The dash captures a decision

Separate when an action is allowed from how it moves the ship.

The dash adds a discrete action to continuous movement. The player asks to start it; the code decides whether it is ready, captures a heading, and carries that heading for the burst. This differs from ordinary movement, which keeps reading the latest input.

DashCycle holds the timing rule. It stores when the dash began and receives the current time as a method argument. IsDashing compares that time with the burst end. IsReady compares it with the burst end plus cooldown. The cooldown starts after travel ends, so the time between possible starts includes both parts.

PlayerDash is the Unity-facing driver. It reads input, checks pause and run-end state, asks the cycle to begin, and passes a heading into PlayerMovement. The heading is normalized when a direction is held; when none is held, the code uses the player's facing. Normalization removes magnitude while keeping direction, preventing a diagonal input vector's larger length from automatically making the burst faster.

Capturing the heading once is a behavior choice. Re-reading input throughout the dash would allow mid-burst steering. Neither choice is a universal rule for dashes; the current code chooses commitment. The separate timing helper makes it easier to reason about readiness without moving a real ship.

Movement state is shared with the camera's PlayerMovement through the static burst state. Moving only the ship would change its relationship to the camera. Player damage checks also consult the dash's invincibility condition. The cooldown is not additional invincibility: the inspected PlayerDash reports invincibility from IsDashing, not from “not ready.”

The guide's statement that the player has no invulnerability frames must be read carefully alongside this source. The dash explicitly provides an invulnerable burst. A post-hit grace period is a different mechanism. Naming both prevents an apparent contradiction and avoids a wrong inference about every damage path.

private Vector2 Heading()
{
    Vector2 held = new Vector2(GameInput.Horizontal, GameInput.Vertical);

    if (held.sqrMagnitude >= HeldThreshold * HeldThreshold)
    {
        return held.normalized;
    }

    // Nothing held, so the ship goes the way its nose is pointing. The
    // flip is the only thing that knows which way that is, and it is the
    // same sign convention PlayerMovement steers by. If it reads backwards
    // on your model, negate it here rather than reversing the flip -
    // SpaceShipPitch documents the same rule for the same reason.
    float forward = player != null && player.DirectionFlipped ? -1f : 1f;
    return new Vector2(forward, 0f);
}

Chapter 11

A boss is a state machine with geometry

Rules decide the phase; presentation makes that phase understandable.

The Leviathan's documented development began with weapon banks firing on timers. The redesign used the banks already present on the model: attack a bank's weak point, silence its attack during the opening act, then fight the exposed hull and the final Scuttle. The historical insight was that geometry already present in the art could become a gameplay rule.

A state machine represents a set of states and rules for moving between them. BossPhaseState holds the current phase and how many emplacements remain. It does not own the boss's health. The emitter supplies health information to it, avoiding another independently changing copy of the total.

Its phases advance in one direction. Destroying the last remaining emplacement advances to Exposed. Reporting sufficiently low health can advance from Exposed to Scuttle. The guard in ReportHealth prevents that transition directly from Armoured. Returning whether a transition occurred tells the caller when to perform one-time phase-change work.

The current user-reported documentation refresh describes a 600-point boss with 240 spent through pods, 270 through the exposed phase, and 90 reserved for Scuttle. Those are reported design values, not a fresh editor measurement. The algorithm itself takes inputs; understanding it does not require memorizing this particular allocation.

Representation changes the problem

The lance was formerly represented by overlapping projectiles. Current source contains BossLanceBeam: geometry rebuilt along a ring arc with separate damage logic. Its source constants describe a 128-unit length and 24 segments. Those numbers describe the implementation inspected for this edition; the visual success of the beam remains unverified here.

A mesh answers “what is drawn.” Damage logic answers “when does the player get hurt.” They need to agree perceptually, but a visible triangle is not automatically a physics collider. Likewise, RotateAround by itself preserves radius; an additional lane-convergence operation can change a round's radius. Explain the complete motion, not just one API call.

The design lesson is broader than bosses: choose a representation that matches the behavior you need. A stream of individual objects and one continuous beam have different geometry, lifetime, collision, and lighting costs. The simpler visual description does not automatically prove lower measured frame time.

Chapter 12

How code becomes an image

Mesh, material, shader, light, and pipeline are different responsibilities.

A mesh supplies geometry such as vertices and triangles. A material supplies a shader and its parameter values. A shader computes parts of the rendering process. The render pipeline organizes the passes that produce the frame. A light supplies illumination information, subject to the pipeline's supported features and budgets.

The Rebuild Reference describes a lava shader using triplanar sampling: blend texture samples projected along different axes so the result does not depend on the island's stretched UV layout in the same way. It then describes two scrolling noise layers modulating emission. The base color preserves the crust while emission carries the hot pattern. This is a lesson in separating two visual responsibilities, not merely making a color brighter.

Emission makes a surface contribute brightness to the image; illumination of surrounding geometry depends on the lighting path. A bright pixel does not independently create a conventional shadow map. Bloom spreads bright image features after rendering; it is not a substitute for light reaching nearby surfaces. The original lighting story becomes easier to understand once these jobs are separate.

Capability is not activation

Think of graphics settings as several gates. Does the active pipeline asset support the feature? Is the runtime setting requesting it? Does the camera or resolved Volume state enable it? Is the necessary scene data available? A row in a menu can change a value while the final image remains unchanged because another gate blocks the effect.

GraphicsDirector creates a runtime override Volume and profile for its overrides. Its source explicitly separates that work from rewriting pipeline assets. That ownership matters in the open editor: mutating shared authored data can affect later sessions. A runtime profile gives temporary overrides a different home.

Why the pickup text moved

The original reference records that pickup captions were soft under temporal antialiasing. Temporal methods reuse information from earlier frames; motion information helps align that history. The chosen solution moved captions onto an overlay canvas composited after the scene's temporal processing. It bought sharp text while making projection, distance scaling, and occlusion the label board's responsibility. A rendering fix moved complexity rather than making it disappear.

Keep SRP batching and GPU instancing distinct. SRP batching reduces CPU preparation and render-state work across compatible draws. GPU instancing can render multiple compatible instances in one draw call. The presence of one does not prove the other was responsible for a measured result.

Source and explanation

The lava and caption histories come from the refreshed Rebuild Reference. GraphicsDirector is the implementation checked for runtime override ownership. Exact active quality settings, asset assignments, and final appearance require the editor or a built player.

Stop & predict

A graphics menu value changes, but the image does not. Is the UI necessarily broken?

Show the reasoning

No. First establish that the UI writes the intended setting. Then inspect the active pipeline’s support, the camera or resolved override, and the required scene data. “The value changed” and “the renderer used it” are different claims.

Explain it in an interviewDistinguish emission, bloom, and illumination. Then explain how you would investigate a graphics setting that appears to do nothing.

Chapter 13

A sound also has owners and units

Trace the signal before reaching for a louder clip.

The project separates a sound's definition from the voices that play it. A SoundDefinition describes a sound and its playback settings. GameSounds holds named sound references and forwards playback requests to AudioDirector, which owns the playback machinery. The historical voice-pool work addresses overlap: a new request should not always have to steal the same source from the previous sound.

Volume is not one number in one place. A clip has its own sample amplitude; a sound has playback gain; channel and master controls may reduce that gain; sources and mixer routing can affect the result. A silent result can originate at several boundaries. Follow the signal path as you followed the experience event.

Decibels express a ratio logarithmically. AudioLevels uses 20 * log10(amplitude) for its conversion and defines a finite floor for silence. Logarithm at zero does not produce a usable finite setting. The inverse conversion uses a power of ten. These operations convert representations; they do not automatically normalize a set of clips or model perceived loudness.

Read the actual playback path before describing its curve. In the inspected AudioLevels code, ToAmplitude returns the clamped slider value, except near silence, and Combine multiplies channel amplitude by master amplitude. The presence of ToDecibels elsewhere does not mean every playback path passes through a logarithmic slider curve. This is a useful example of why a helper's existence is not proof of its use.

Saving is separate from changing

SettingsStore marks preferences dirty and postpones the disk flush using unscaled time. Each new change moves the deadline. That is debouncing: wait for activity to settle rather than writing on every intermediate slider position. It also flushes on focus loss, application pause, and quit. A crash can still happen before a pending write reaches disk; this reduces exposure rather than guaranteeing durability.

Does turning channel and master controls down add their amplitude values together?

Show the reasoning

No. This implementation multiplies the two amplitude factors. Each scales the signal left by the other. Decibel changes can be added when expressed as compatible logarithmic gain ratios, but these two inputs are amplitude factors in this method.

Chapter 14

Measure the mechanism

Optimization is a claim about cost, not a synonym for shorter code.

The historical profiling story includes a diagnostic overlay that caused a rhythmic hitch. Comparing captures with the overlay visible and hidden helped isolate its process-counter sampling. The lesson is that measurement has a cost and a measurement tool can change the system it observes.

Start with an observation: a frame takes longer. Form a hypothesis: some periodic operation contributes. Change or isolate that operation, compare under relevant conditions, and explain what else changed. Correlation points you toward a suspect; it is not a complete causal argument.

Separate allocation from garbage collection. Allocating managed memory and reclaiming unreachable managed objects are different operations. Instantiate and Destroy can also involve engine-side work. A capture with no recorded garbage-collection event does not prove creation and destruction were free. Equally, introducing a pool does not prove the game became faster.

Pooling trades repeated creation for retained instances, reset work, and lifetime complexity. Warmup moves some cost earlier and retains memory. A failure to reset health or firing state can cost more than the allocation it avoided. The project adopted pooling broadly, but the original reference itself distinguishes measured results from benefits that had not been demonstrated.

Read distributions as well as averages. A median describes the middle; high percentiles expose slower frames. CPU time, GPU time, and waits are not interchangeable. A thread waiting to present a frame is not necessarily executing expensive gameplay. Frame caps and synchronization also change the timing context.

DynamicResolutionController is a feedback controller: it compares observed frame time with a target, lowers scale when the frame is too slow, and recovers more slowly when there is headroom. A deadband leaves small differences alone to avoid continual corrections. Its clamps bound the output; its response to a measurement is not proof that the active renderer honored that output.

Stop & predict

You reduced allocations, but the hitch remains. Was the experiment useless?

Show the reasoning

No. It can narrow the explanation, provided the capture confirms the intended allocation change under comparable conditions. It does not justify claiming a performance win that did not occur. Record both the mechanism changed and the result that stayed the same.

Explain it in an interviewDescribe one optimization as hypothesis, experiment, observation, and limitation. What evidence would make you abandon the hypothesis?

Chapter 15

A test makes a specific claim

Learn to read a test as an executable argument.

A unit test puts a small piece of behavior under controlled conditions and checks an expectation. The useful question is not merely whether it passes. Ask what defect would make it fail, and what defects could remain while it still passes.

The kill-reporting test below uses fixture values chosen to exercise a boundary. They are not enemy balance values. First it creates a health object that the next hit will kill. Then it applies further hits. The assertions require the fatal transition to report true once and later calls to report false.

Arrange establishes the conditions, act performs the operation, and assert checks the result. A test may alternate acts and assertions to examine a sequence. Here that sequence is essential: testing only the first fatal hit would miss repeated kill reports.

Read the project code · HealthStateTests.cs

Assets/Tests/EditMode/HealthStateTests.cs · lines 62–69 · source snapshot

public void TakeDamage_ReportsTheKillOnlyOnce()
{
    var health = new HealthState(1);

    Assert.IsTrue(health.TakeDamage(1));
    Assert.IsFalse(health.TakeDamage(1), "a second hit must not re-award the kill");
    Assert.IsFalse(health.TakeDamage(99), "overkill must not re-award the kill either");
}

This protects the health object's contract. It does not prove that an enemy is wired to use the return value correctly, that a collider delivers the event, or that a built player displays the reward. Those are integration and play/build verification questions. A large suite of narrow tests is not automatically broad coverage.

The codebase's ordinary rule classes make focused tests convenient: HealthState owns a small state machine, SpawnMath accepts explicit time, and SkillPool accepts a selector. Not every one is a pure function, and some still depend on Unity types. The benefit is that the behavior can be exercised without constructing the entire game.

For a study exercise, mentally remove the early killReported guard. Predict which assertions fail before running anything. Then explain why. This is stronger practice than reading a green result because you must connect a line of code to an observable contract.

Also distinguish test isolation from production cleanup. GameInput tests restore their installed source in TearDown. That is why one test does not intentionally leave its fake for the next. A global substitute is convenient but makes cleanup part of the test's correctness.

Stop & predict

Would a test that copies TakeDamage’s implementation and compares the two be convincing?

Show the reasoning

Not by itself. It could reproduce the same mistake. Tests should state independently meaningful behavior: no second kill report, no healing beyond the maximum, or a stable result for explicit inputs. The assertion needs a reason beyond “that is what these lines currently calculate.”

Explain it in an interviewChoose an existing test. Explain the failure it catches, a defect it does not catch, and why both boundaries matter.

Chapter 16

There are several versions of “the game”

Source, authoring tools, the live editor, and a shipped build are separate evidence.

A runtime script defines behavior used during play. An editor script can create or configure assets before play. BuildBossRig is an authoring tool: its constants and construction code describe what it will author when run. Reading that file does not prove an existing prefab was rebuilt from it.

The distinction matters because the Unity editor can hold unsaved state that differs from the file on disk. After editing C#, a successful recompile must load the intended assembly before runtime inspection can test the new behavior. A player build then has its own compiled code and packaged data. An answer about one of these layers is not automatically an answer about the others.

C# source→ compileLoaded assembly→ buildShipped player

Namespaces and assemblies also belong to different layers. A namespace qualifies a type name in C#. An assembly is compiled output. Assembly definition files establish compilation groups and references. This project uses SurvivalChaos and SurvivalChaos.Editor assemblies, while the editor-tool namespace can be SurvivalChaos.EditorTools. A matching-looking name is not proof of identity.

The agent guide records the safe workflow for this particular machine: the inner folder is the repository and Unity project; builds go to an absolute path under the outer Builds folder; serialized assets are changed through the running editor; agents coordinate relay access. Those are environment rules. They should remain in the guide rather than being rediscovered from an old lesson.

For interviews, this is a lesson in reproducibility and evidence. “I changed the source” is a useful fact. “The loaded method reflects that change” is a stronger and different fact. “The built player behaves correctly under the tested conditions” is stronger again. Say which claim you actually verified.

Stop & predict

An authoring constant changed, and C# compiles. Must the existing prefab now contain the new value?

Show the reasoning

No. The authoring operation must actually apply the value to that prefab, and the editor must persist the intended result. A constant in an editor tool is not a live binding to every asset it once created.

Explain it in an interviewHow would you establish that a fix exists in the shipped build rather than only in source or an editor session?

Chapter 17

Turn the project into interview evidence

Practice explanations you can defend, not sentences you can recite.

A good project answer has a concrete trigger, a rule you needed to preserve, a decision, and evidence. Use “we” for the original team's work and be precise about what you implemented, reviewed, tested, or learned during the rebuild. Understanding an AI-assisted change is valuable; claiming authorship you cannot explain is fragile.

Try the following prompts aloud. Open the relevant source only after giving your first explanation. Then correct your answer using what the code actually says.

  1. Objects: Explain why shared enemy configuration does not imply shared current health.
  2. Abstraction: Explain what an interface made replaceable and what it did not guarantee.
  3. Lifetime: Explain why reusing an object requires preparation and why reloading a scene does not automatically reset every static.
  4. Math: Derive angular motion from a linear speed, carrying the units through.
  5. Design: Explain why drawing an upgrade does not consume its pick limit.
  6. Rendering: Explain why a bright object, a light, and bloom are different.
  7. Debugging: Explain how you would locate a missing reward between collision, state change, event, and UI.
  8. Evidence: Explain what one test or profiler capture establishes and what remains unknown.

A useful answer shape

“When this event happened, the old implementation could produce this symptom. We needed this rule to remain true. The change put that rule in this place. We checked it using this evidence. That check did not cover this remaining condition.”

For the health example, the key idea is a once-only transition report. For input, it is replacing the dependency without changing every caller. For the boss, it is state progression with one health owner. These principles transfer to other games and to non-game software because they concern state, boundaries, and evidence.

A reading route for the source

Start with HealthState and its tests. Follow Enemy into EXP and Player. Read ISkillTarget beside one skill, then GameInput beside its fake. Follow VictoryMenu into RunOutcome before reading the pool. Study PlayerMovement with a units notebook. Then read SkillPool, BossPhaseState, and the rendering and settings owners. That order gives each larger system prerequisites you have already practiced.

What “understood” should mean

You can predict a small change, explain why it changes the result, and name a case your explanation does not cover. Use the chapter checkboxes as a private study aid, not as a certificate that a system has been tested.
