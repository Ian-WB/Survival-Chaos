Part I

Where the project started

Survival Chaos was built in 2023 by a five-person team at PUC — the commit history is in Portuguese, and the last activity before the revival was a build handoff in June of that year. It ran on Unity 2021.3 with URP 12.

The game is an orbital survival shooter. You fly a ship in a circle around a volcanic island floating in space, always facing the centre. Enemies converge from outside and settle into the same circular lane. You survive ten minutes, a boss arrives, and you fight it.

That circular structure is the single most important thing to understand about the project — nearly every system is expressed in terms of it, and several of the stranger pieces of code only make sense once you see it.

Before the rebuild began, the project had already been moved to Unity 6 and URP 17. That migration worked, but it was the only thing that had been done: the code underneath was untouched jam code.

Part II — the rebuild

The initial read

The first pass was diagnostic: read everything, run nothing, report honestly. What it turned up set the agenda for everything after.

Live defects

  • ColliderScript threw a NullReferenceException every time an enemy passed the player — it called GetComponent<BossMovement>() unconditionally, and regular enemies don't have that component.
  • Enemies and the boss awarded experience from Update() after already destroying themselves in OnTriggerEnter. It worked only because Unity defers Destroy past the end of the frame.
  • The player's health bar never updated when hit by enemy bullets — only by collisions. Bullet damage was invisible until you died.
  • One skill was unreachable: MoreAttackSpeed was written but never added to the pool. The pool also emptied permanently after two picks, so every later level-up silently became a heal.

Structural findings

  • BossMovement was a 76-line duplicate of EnemyMovement — and it was disabled on the only prefab that had it. Its Update() had never run.
  • BossScript held 32 individually named muzzle fields and roughly 90 hand-written Instantiate calls.
  • 21 spawner objects were placed by hand in the scene, each with its own copy of the same timing fields.
  • Every material was untextured flat colour. There is not one texture in the original art.
Why this mattered

Several of these weren't visible as bugs. The disabled BossMovement, the deferred-Destroy reward, the unreachable skill — all of them looked like working features. Reading the code carefully found things that playing the game never would.

01

Structure

Assembly definitions and a test harness, so that everything afterwards could be verified rather than hoped at.

SurvivalChaos.asmdef pulls the runtime scripts out of Unity's catch-all assembly. SurvivalChaos.Tests.EditMode.asmdef adds an edit-mode test assembly, gated behind UNITY_INCLUDE_TESTS so it never reaches a build.

Namespaces were deliberately not added to the existing files at this point. Unity 6 uses C# 9, which has no file-scoped namespaces, so wrapping them would have meant reindenting every file — hundreds of lines of pure whitespace noise on code that was about to be rewritten anyway. New code got the namespace; old code was to pick it up as it was replaced.

Most of it never was replaced, because it did not need to be — it was hardened in place instead. The last twenty-three files were wrapped in one pass much later, when the argument had inverted: the count was down, the churn was one wrapper and an indent per file, and the cost of the split had become concrete rather than theoretical. Referring to these types from outside meant knowing which of them were global, which is a thing to know for no reason.

02

Input

The Input System package wasn't cached locally and pinning an unverified version risked a project that wouldn't compile. So the order was inverted: build the abstraction first, backed by the old API, then swap the backend.

gameplay scripts → GameInput → IGameInput → Legacy / InputSystem

All 12 call sites moved onto GameInput. When the package did land, the swap was one new class — InputSystemGameInput — and zero gameplay scripts changed.

A detail worth keeping

The old Input Manager smoothed its axes; the Input System reports keys digitally. A direct port would have made the ship noticeably twitchier — a silent change in feel you'd struggle to attribute. The new backend reproduces the old ramp using the Input Manager's own defaults, so the swap changed nothing you can feel.

03

Content model

Three systems moved out of code and into ScriptableObject assets you can edit without recompiling.

Skills

SkillSelect went from a ~100-line hardcoded state machine to a thin driver over SkillPool. Both original bugs died structurally rather than being patched: every skill is now an asset in the pool, and Heal is authored with maxPicks: 0 — unlimited — so the pool can never run dry.

Enemies

The prefabs revealed something that justified the whole approach: the same script carried different tuning per prefab. Enemy_1 was 7 HP on one prefab and 2 on another, while the experience reward was a hardcoded field on the script — so two prefabs sharing a script physically could not differ in reward. Health was per-prefab data; reward was per-script code. EnemyDefinition puts both in one asset.

Waves

21 hand-placed spawners became one WaveDirector plus a single MainRun asset holding 19 streams. The extraction read the live scene rather than retyping values, so the tuning transferred exactly.

What the scene was hiding

Two of those 21 spawners sat on the ExitButton objects inside the death and pause menus. One would have spawned a boss five seconds after you paused. They were inert only because timeScale is 0 while those menus are open — a load-bearing accident. They were excluded from the migration and deleted.

04

The boss

Behind 32 named muzzle fields and ~90 Instantiate calls there were only ever three attacks. BossEmitter expresses them as a list you edit in the Inspector.

The six unused delay fields left in the old script — initialDelay1/2/3, spawnDelay1/2/3 — were reaching for per-attack timing. That's exactly what BossAttack now provides, so they're gone and the capability they sketched is real.

After the phases

The work since has been feature and presentation rather than architecture.

  • A victory condition — the game genuinely had none. Killing the boss awarded experience and nothing else.
  • Ship animation — smoothed, frame-rate-independent motion replacing instant rotation snaps.
  • An HDRP branch — pipeline migration, a rebuilt sky, and a procedural lava shader.
  • A world-scale pass — the entire game reduced to one tenth its former size.
  • Bullet lights — a pooled lighting system for player projectiles.
  • Upgrades as pickups — level-ups became a choice on the ring rather than a free grant.
  • A real quality tier system — four tiers, three of them Unity's own assets, and a graphics screen where every row does what it says or says why it cannot.
  • Git LFS — the history purged of roughly 1.1 GB of deleted build artifacts and the binaries migrated, taking git down to 2.7 MB against 533 MB in LFS.
  • Effect timing and an emissive ladder — retire timers cut from 36.4 s of held effects to 18.9 s, and every glowing surface put on one brightness scale.
  • Named upgrades — each pickup now says what it is, drawn on the overlay canvas where temporal antialiasing cannot reach it, and hidden when the volcano is in the way.
  • A run twice as long, and a build to fill it — ten minutes instead of five, with the spawn ramp stretched to match rather than extended, and twenty upgrade picks where there were eight.
  • Encapsulated scene wiring — sixty-nine public runtime fields taken private, so a scene reference is no longer something any script can repoint.
  • One namespace — the last twenty-three jam-era files wrapped in SurvivalChaos, closing a split that had been deliberate and had stopped being useful.
  • A taller arena, and the spawns lifted to match — the player's vertical band raised by 3.3 units, and all nineteen spawn heights rescaled into it after four streams were left stranded beneath the new floor.
  • A gamepad — analogue sticks straight through and digital sources ramped, added behind the input abstraction without a single gameplay script changing.
  • Feedback for landing a shot — enemy hulls flash on a non-fatal hit, the experience a kill was worth rises where it happened, and the health bar flinches when it drops.
  • An end-of-run summary — time survived, level, kills, experience and the build taken, written into the empty third of the card both endings already put up.
  • A dash — 0.22 s of invincible travel on a 1.22 s cycle, added because the boss's second act needed a verb the game did not have.
  • The boss rebuilt as three acts — weak points, telegraphed attacks and guns that turn with the ship, out of the muzzles that were already on the model.
  • Unity 6.6 — a minor engine version, five unused packages gone with it, and the deprecated build symbols retired.
  • An editor the terminal can drive — Unity's CLI and the Pipeline package in place of the AI Assistant relay, which closed the write-compile-verify loop without touching the editor window.

The script review pass

With the architecture settled, every script was read end to end — all 88 of them, in one pass, looking for defects rather than for things to redesign. It turned up 22, all since fixed.

The distribution was the interesting part. The systems written during the rebuild came through almost clean: nulls guarded, statics reset, frame-rate-dependent maths deliberate and covered by tests. Nearly every defect sat in the 2023 code that hadn't yet been rewritten — Player, EnemyMovement, Timer, PauseMenu, ExpBar, the ColliderScript family.

Two corrections worth recording

The review claimed the rebuilt code was clean and the problems were all in the jam code. The test suite disproved that: BarMotion — new code, and the most delicate timing in the project — held the single worst defect, and EmptyingCompletely_ReachesZero had been failing all along. It was read past because it reads well.

And one fix was itself wrong. The vertical-chase threshold of 15 was called unreachable because it exceeds the orbit radius of 13.72 — but both the enemy and the player sit on the ring, so the distance between them runs to the diameter, 27.44. 15 covers about a 66° arc. Replacing it with a tenth of that collapsed the band to ~6° and the chase all but stopped, which only showed up in play.

Part III — how it works

The arena and the orbit model

Start here. Almost everything else follows from it.

Every distance on this page is at the current scale

The world was rescaled by ten after most of this was written. Figures describing how things stand now are given at the current scale — an orbit radius of 137.2, a 370-unit island, bullet lights of range 100. Passages recounting a past change keep the numbers that were true when it happened, so a diameter of 27.44 in the review notes above and one of 274.4 today are the same fact ten times apart.

The island sits at the world origin. Everything that moves does so on a circle around the vertical axis through that origin. ArenaGeometry.OrbitRadius — currently 137.2 — is the radius of the lane enemies converge to and hold.

How things get onto the lane

SnapToOrbit runs at Awake and projects its object onto that circle, keeping its bearing and height and changing only its distance from the axis. The Player uses it with an offset of 0; the camera uses an offset so it trails at a fixed distance behind.

Enemies get there differently — EnemyMovement flies inward until it's within OrbitRadius, then switches to orbiting.

The part that surprises people

Movement around the circle is angular, not linear. PlayerMovement and ShootScript both call RotateAround, whose third argument is degrees per second:

float degreesPerSecond = orbitSpeed * Mathf.Rad2Deg / ArenaGeometry.OrbitRadius;
transform.RotateAround(pos, Vector3.up, -h * Time.deltaTime * degreesPerSecond);
transform.LookAt(pos);

Projectiles orbit too — they don't travel in straight lines, they sweep around the arena at their own angular rate.

The number the inspector was lying about

The player's two speeds used to be authored in different units and shown side by side as though they were the same thing. Speed was 32 degrees per second and Up_Down_Speed was 5 world units per second, so 32 sat next to 5 looking six times larger while the ship was actually only about half again as quick sideways as it was vertically. There was no way to see that from the Inspector.

Both are units per second now, named Orbit Speed and Climb Speed, and the conversion to the angle RotateAround wants happens in code. Set equal at 70, the ship covers the same ground in both directions.

The conversion divides by the lane's radius, not by the object's own. That distinction is load-bearing rather than incidental: the Main Camera runs this same component 100 units further out, so measuring against its own distance from the axis would hand it a smaller angle than the ship and leave it trailing a little further behind every second. Both derive 29.23 deg/s from the same authored number, which is what stops them drifting apart.

Why this matters practically

When the world was scaled to one tenth, these values needed no change at all — an angle is an angle regardless of radius. The same is true of enemy approach code, which moves by an unnormalised direction vector and is therefore proportional to distance. Only genuinely linear rates like the climb speed had to scale. That's why a change that touched 34 values didn't wreck the game's feel.

ApplyBounds clamps the player vertically against a BoxCollider2D named PlayerBounds. It used to clamp world X from the same box as well, which is meaningless for a craft that orbits an axis — X is not a limit there, it is where you are around the ring, and clamping it would have pinned the ship at two points on the circle and fought RotateAround. It never fired only because the authored box was 53.9 wide against an orbit radius of 13.72, so it was a trap waiting for someone to narrow the box rather than a feature. The vertical envelope is the whole job now, and the box is the authority on it: TryGetBand hands the two numbers out so that nothing else keeps a copy.

The gamepad arrived without touching a gameplay script

The abstraction was built in Phase 2 on the argument that a backend could be swapped behind it. Adding the pad is the second time that has paid: one file changed, InputSystemGameInput, and nothing else in the project knows a controller exists.

A stick must not be ramped like a key. The smoothing in that backend exists to reproduce the legacy Input Manager's sensitivity and gravity, because the Input System reports keys digitally and raw keys made the ship twitchier than it was. A stick already reports how far it is pushed, so putting it through a rate limit would add lag to the one input that never needed any — the ship would lean into a turn a fifth of a second after the stick did. Analogue sources pass straight through; digital ones ramp. The d-pad counts as digital and is routed in beside the keys, because it is the same kind of signal wearing different hardware.

Handing back matters as much as taking over

The stick wins outright while it is deflected and releases to the ramp, still holding the value it left there. So centring decays from where the stick was rather than snapping to zero, and a key pressed afterwards carries on from there rather than from a standstill. Both devices stay live at once, with no mode to switch and nothing to detect.

No deadzone is applied in the project's own code. Gamepad.leftStick already carries the layout's stickDeadzone processor, reading 0.125 to 0.925 from this project's InputSettings: a stick pushed to 0.50 arrives as 0.538. A second deadzone stacked on top would rescale an already rescaled range and quietly cost the player the top of their travel.

The debug bindings stay on the keyboard. F3, F4 and F7 exist to be deliberate, and there is no face button a player will not eventually press by accident.

A / D is throttle, not steering. The ship's nose already points along its direction of travel, so those keys accelerate it forward and backward along the lane. This tripped up the ship animation work and is worth remembering.

The player

Movement

PlayerMovement orbits and looks at the centre; ApplyBounds clamps height. The Main Camera runs the same PlayerMovement component with the same speed — that's how it stays in sync, rather than following the player.

Shooting

Player.Shoot() is driven by InvokeRepeating at spawnDelay (0.5s). The pattern comes from a table of vertical offsets indexed by how many shot upgrades have been taken, measured in multiples of shotSpacing (4), and rotate — the flip state — decides which of the two projectile prefabs counts as forward. The stages run 1 → 2 → 3 → 6 bullets. There used to be a fifth, Back Shot, which fired five forward and four the other way round the ring; it was the one pick that changed what the gun does rather than how much of it there is, and it retired along with the backward table when the progression was stretched.

The ship model

SpaceShipPitch animates the visual only. It reads Player.DirectionFlipped rather than tracking its own copy — the two used to be toggled independently by the same key, which meant any frame where one saw the input and the other didn't left the model facing the wrong way permanently.

Easing uses an exponential form that settles the same amount per unit of time, not per frame:

Mathf.Lerp(current, target, 1f - Mathf.Exp(-response * deltaTime))

The common shortcut — Lerp(current, target, response * deltaTime) — feels different at 30fps and 144fps. ShipMotion is separated out precisely so this can be tested.

Skills depend on ISkillTarget, not on Player — which is what lets selection be tested without a scene. SkillPool takes an injectable random function for the same reason.

Healing is no longer one of them

Heal used to sit in the pool as the unlimited entry, which meant the commonest way to meet healing was as one of three pickups on a level-up — so taking the heal forfeited two upgrades, and taking an upgrade forfeited the heal. That is a trade between a reward for killing well and the thing you need when you are not, and it is not a decision worth putting in front of anyone.

It arrives on its own cadence now, every second level, outside any offer. SkillSelect filters the type out of its pool in code rather than trusting the scene list, because putting it back is a single click with a confusing symptom.

Two consequences. Healing is weaker — the skill restored 5 and a health drop restores 2. The pool used to run dry, since the three upgrades totalled eight picks between them and a run reached the end of its build around level nine. There are twenty picks now, across four upgrades, and the stretched run pays out enough to earn all of them — so the empty draw is a guard rather than the usual ending. It still sends health out when it happens, because a level-up that puts nothing on the ring reads as broken pickups rather than as a finished build.

The sextuple shot fired five

Stage three spawned four extra bullets plus the base one. The name said six, the banner said "SexTUPLO Shot!", and the count said five. The one-line fix would have been lopsided: every other stage puts a shot dead centre and pairs the rest around it, which only works for odd counts, so a fifth extra would have spanned −2 to +3 spacings.

The pattern is a table of offsets now, one row per stage, with the sextuple row shifted half a step so its six sit symmetrically about the pivot. That also collapsed about seventy lines of near-identical spawn calls — the same five patterns written out twice, once per direction of travel, which is exactly how a sextuple that fired five went unnoticed.

Enemies and waves

One WaveDirector reads MainRun.asset and runs a coroutine per stream. Each SpawnStream carries what to spawn, where, and how its cadence tightens.

Nineteen doors, and the player learns where they are

Each stream authored a single world position plus a random offset to add to it — and xOffsetRange was {0, 0} on all nineteen. No horizontal spread was ever filled in, so enemies arrived from nineteen fixed compass points and varied only in height.

A stream now sends its enemies in from a random bearing, keeping the distance from the axis and the height it was authored with. That preserves what actually distinguishes one stream from another — this one comes from 22 units out at head height, that one from 40 — and varies only the direction. The authored rotation stops mattering within a frame either way, because EnemyMovement looks at the axis every update.

The opt-out is called lockBearing rather than randomiseBearing on purpose. Unity keeps what it has already serialized and zero-fills fields it has not seen, so a bool meaning "randomise" would have arrived false on all nineteen existing streams however its initializer was written, and the spread would have quietly not happened. False has to mean the useful thing.

SpawnMath.IntervalAt() derives the current gap from elapsed time in closed form. The original ran a second coroutine that repeatedly multiplied its own delay field, which meant the only way to know the spawn rate at a given moment was to run the game.

The floor moved, and four streams stayed where they were

The player's vertical band is a box in the scene. The heights enemies arrive at are numbers in a wave asset. Nothing connected the two, so when the band was raised — floor from 1.103 to 4.421, ceiling from 11.129 to 13.318 — the spawn heights did not move with it, and four of the twelve obstacle streams, authored at 2.9 and spawning over 1.8 to 3.7, ended up entirely beneath the floor.

It only showed on one enemy, and that is what made it hard to see. Three of the four enemy prefabs carry EnemyMovement, which climbs towards the player once inside its 164.6 chase radius — so those spawn low, notice, and fix themselves within seconds. Enemy 3 is the only one carrying ObstacleScript, and that script has no orbit branch and no chase branch at all: it flies inward in X and Z, reaches the orbit radius, and then holds its spawn height for the rest of its life. Six distinct heights before, six after.

The rescale fixes the instance, not the mechanism

Moving the box again would break it again, silently, and again only on Enemy 3. So the gap is checked now. SpawnBand holds the arithmetic free of scene types so it is directly testable; ApplyBounds.TryGetBand exposes the band; and WaveDefinition.DescribeStreamsOutside takes the band as a parameter, because an asset can be opened with no scene loaded.

It reports and never repairs. Whether the streams or the bounds are the wrong half depends on intent, and guessing between them would be worse than saying so. It does separate a stream that straddles the floor from one wholly beneath it, because losing some of a stream and losing all of it are different problems.

WaveDirector runs the sweep at Start, editor-only — not from OnValidate, which fires when the component is touched and not when either of the two things it compares changes. Pressing play is the one action that reliably follows editing a wave or a bounds box. Survival Chaos › Waves › Check Spawn Heights runs the same sweep on demand.

A first balance pass

The complaint that prompted it: the player feels too powerful, from the first minute. The numbers agree. A full build was three attack-speed picks and four shot upgrades, which is a fire interval of 0.216 s and eight projectiles — 37 bullets a second against a starting 1. Enemy health did not scale at all, so Drones and Scouts died to one bullet at minute one and at minute five alike, and the only thing pushing back was spawn rate.

Time-scaled health was considered and rejected in favour of fixed values that climb with the enemy's own tier, plus the existing spawn ramp. The Drone went from 1 to 3 — it is the enemy twelve of the wave's streams spawn, so it is what the player actually fights — and the Heavy came down from 7 to 5. Scout and Fighter were already where they should be.

Both of the things that pass did not fix have since been dealt with, and they turned out to be one problem wearing two coats. Attack speed compounded because it subtracted a fraction of the current interval, so each pick was worth less than the last and the third was nearly worthless; and the build ran out at level 9 because 3 + 4 + 1 was every meaningful pick. Making each pick a flat share of the starting rate fixed the first and made more picks worth having, which fixed the second. See the run and the ladder below.

Showing that a shot connected

Multi-hit enemies made a missing effect into a real bug

Enemy.cs never spawned a hit effect. It did not need to: until the Drone went to three health, every enemy on that script died to one bullet, so the explosion was the hit feedback. Enemy_1.cs had a spark; Enemy.cs did not — and Enemy.cs is what the Drone runs. Two of every three shots at the most common target in the game produced nothing at all, which is the worst thing a shooter can do: a shot that lands looking exactly like a shot that missed.

Worse, the field existed in code before it existed on disk. Unity only serialises a newly added field when the prefab is next re-saved, so Enemy 2 and Enemy 3 had no enemyHit entry at all — which is why an early test of the health change appeared to do nothing.

Both scripts now follow one rule: a spark for a hit, an explosion for a kill. Enemy_1 used to play the spark on every hit including the fatal one, so a kill fired both and the two outcomes read as the same event — exactly the distinction multi-hit enemies need legible. Effects spawn at the bullet's position rather than the enemy's centre; on a ship several units wide those are visibly different places.

The effects themselves come from a bought pack, which ships the way packs do: one container prefab with every effect parented under a single root, laid out side by side so they can all be seen at once. Convenient to browse, useless to spawn — ObjectPool.Spawn takes a prefab, and a child of a prefab is not one. EffectPrefabExtractor splits the container and fixes three things on the way out that are each easy to miss by hand across a pack:

  • Local transforms are zeroed. In the container every effect sits at its own offset so they do not overlap on screen. Spawn positions the root, so an inherited offset would put every explosion a fixed distance from whatever it was meant to be on — consistently wrong, and it would look like a bug in the spawn code.
  • Looping is turned off, with prewarm alongside it. Packs loop their showcase prefab so effects play continuously while you scroll past them; spawned from the pool that restarts forever, and the only thing ending it is the retire timer cutting it off mid-cycle.
  • DestroyAfterTime is added, with the delay measured from the longest duration-plus-lifetime under the effect rather than left at the ten-second default. These fire on every hit — a quarter-second spark held for ten seconds keeps forty finished objects alive per second of combat, all of them drawing nothing and all of them still in the pool's active set.

Health and death

HealthState holds the rule that matters: TakeDamage returns true only for the hit that kills, and only once. That's what makes death effects and experience impossible to fire twice, and it removed the dependency on Destroy timing entirely.

The boss

It was a wall that sprays. All three attacks fired every muzzle they owned, simultaneously, forever, on fixed timers — no phases, no telegraph, no weak points, and no reason to be at any particular height. The hull took damage anywhere, so the correct play was to hold the trigger and hope, and 300 hit points were the only thing making it last.

Almost none of what replaced it is new content. The 32 muzzles are not scattered: they cluster into three banks at three heights, and those heights land on the floor, the middle and the ceiling of the band the player can fly in. Nothing in the fight knew that.

The guns did not turn with the ship

This blocked everything else

EnemySpaceShip rotates the model 90° either way to face the direction of travel, and RingChase makes the boss reverse every time the player crosses its bearing. All 32 muzzles were parented to the Boss root, which only ever faces the middle of the arena — so the ship turned and the guns stayed where they were, and half the time the boss fired out of its own tail. The prow muzzle swings 87 world units between the two headings.

A telegraphed attack is meaningless if the muzzle is not where the barrel is, so nothing else could be built until this was fixed. Three emplacements, and why they are where they are

Each sits at the centroid of its own bank's muzzle heights, averaged from the model at build time rather than typed in, so a pod cannot drift away from the guns it stands for. They land at world y 53.8, 91.7 and 127.1 against a playable band of 44.2 to 133.2 — floor, middle, ceiling.

They are mounted proud of the hull, which is not decoration: the hull is a trigger that eats bullets, so a target inside it could never be hit at all. Wrecking one silences its bank for the rest of the fight, so the order the player kills them in is a difficulty dial they set themselves.

The boss stopped climbing to meet the player

That is the one real behaviour change, and it had to go. The pods sit at fixed offsets from the hull, so a boss that matches the player's altitude parks the crown pod 49 units above them — above whatever height they climb to, forever — and the fight loses a third of itself to a weak point that cannot be reached.

Nothing is lost by holding station. The hull is 156 units tall against a band of 89, so it already spans every height the player can occupy; matching their altitude never changed whether the boss could be flown over, only where its guns pointed. This is the one enemy in the game that is a wall rather than a chaser.

The second act had lost what the first one was about

Armoured is a fight about height. Exposed threw that away: with the hull spanning the whole band, any height is as good as another, and what was left was holding the trigger through 120 hit points and dashing once every seven seconds.

Wreckage puts the three heights back with their meaning reversed. The boss sheds plates of its own hull from the emplacements the player themselves destroyed, at those emplacements' own heights. The places that were worth flying to become the places worth avoiding, and the player already knows where they are.

The plates do not move. Everything else in this arena rides the ring; these are the one thing that does not, which is what makes them read as debris rather than as another attacker — and it means the boss, cruising at 15° a second while it sheds, leaves a wake of its own hull and eventually comes back round into it. Life over cadence is the tuning: 16 seconds against 1.8 holds about nine plates, three at any one height, which against a player lapping the ring every 12.3 seconds is a forced move every four seconds or so. Three shots break one, and breaking it earns nothing — clearing a lane is the whole of its reward.

One collision has to cost one hit, and the obvious fix was the wrong one

Contact was billing far more than a hit. The first guess was the plate's shape, on the theory that a tumbling box sweeps the player in and out of itself; the collider became a sphere and it changed nothing. What turns is the player — PlayerMovement aims the ship at the arena's axis every frame and SpaceShipPitch rolls it, so a ship inside a stationary trigger keeps carrying its own collider back out through the surface and in again, and every one of those is a fresh OnTriggerEnter.

Measured with the spawner stopped and the arena verifiably empty, one plate took a stationary player from 19 hit points to 0 in 0.64 seconds — close to one hit per physics step, and invisible, because this branch of Player spawns no hit effect to count. The plate goes intangible the moment the player is inside it and solid again once they are clear; the same test then costs exactly one hit and nothing more over six seconds.

Three quarters of the boss's fire could not reach the player

Two defects found while measuring

BossEmitter resolved the health bar once, in Start, and Timer switches that bar on at the same second in the run that the spawn stream releases the boss. A tag search does not see inactive objects, so whichever of the two Unity happened to run first decided whether the boss had a working health bar for the whole fight — and the failure is silent, because the fight plays correctly and the bar just sits full. Resolved on demand now.

HitFlash claimed every renderer beneath it, which would have meant a shot breaking on the armour lighting up the three pods exactly as brightly as a shot that hit one. It leaves renderers that sit under a nested flash to that flash now, so the hull lights one renderer and each pod lights its own. That distinction is the whole of the first act.

VolleyTimer schedules the next shot relative to now rather than to when it was due, so a frame spike delays the cadence instead of firing a catch-up burst.

It used to arrive on two clocks

Timer does not spawn the boss. It counts the run out and reveals the health bar; the boss itself comes from a spawn stream in the wave asset like everything else. That is two numbers for one event, in two files, with two owners — and they agreed only because someone had typed 600 into both.

Why that is worse than it sounds

Neither half of the drift is visible while authoring. Move the boss in the wave asset and the health bar is left behind; move the timer and the bar goes up in front of an empty arena. Both look perfectly correct in the Inspector and both surface ten minutes into a run, which is the most expensive place in this project to learn anything.

WaveDefinition.BossArrivesAt now derives the time from the boss's own stream, finding it by what it spawns — the only prefab in a wave carrying a BossEmitter. No new field, because a second field holding the same number is a second field that can disagree with it. The serialized value stays as a fallback for a scene with no director, and a disagreement is reported rather than quietly corrected: a number left in the Inspector that has stopped meaning anything is the same trap in a new place.

Progression and ending a run

EXP is a singleton event bus. Enemies call EXP.Instance.AddEXP(); Player subscribes and accumulates. At the threshold it counts the level, calls SkillSelect.PickSkill(), raises the requirement by 35, and continues.

A level-up is a choice on the ring

Levelling used to apply a random skill the instant the bar filled. That is the single biggest reason the player felt strong from the first minute: every upgrade was free, arrived without being asked for, and cost no attention at a moment when attention is the only currency the game charges.

Three glowing pickups now go out around the orbit instead, spaced far enough apart that they cannot all be reached — committing to one is giving up the others, which is the whole point of handing upgrades out this way. A skill is drawn from the pool when the offer goes out but charged against its pick limit only when one is actually collected, so the two the player flew past are still available next level. An offer is not a pick.

Health rides along on its own cadence, every second level, and is not part of the offer. Pickup.Offer stays null on a health drop, so the code that clears the rest of an offer walks past it in both directions: taking the health forfeits no upgrade, and taking an upgrade does not clear the health.

Sharing the ring is not the same as sharing the forfeit

Health and the upgrade offer were first placed by two separate calls, each asking the placement helper for its own bearings from the same player position with its own coin flip for direction. The nearest bearing of a set is the same number whatever the set's size — the clearance is clamped by the step but not scaled by it — so whenever the two flips agreed, the health drop landed exactly on top of the first upgrade. Measured before and after: nearest pair 0°, then 90°.

A level-up is one placement now. Health takes a slot at random rather than always the nearest or always the furthest, because either fixed choice teaches the player which pickup to fly at before they have looked at what is on offer.

Naming what is on offer

Three coloured shapes are not a choice. The pickups were told apart by tint alone, on the reasoning recorded in SkillDefinition: there is no room for a label on an object the size of a bullet, and no time to read one while dodging. That holds for the health drop, which is only ever something to go and get. It does not hold for an offer, where deliberating is the point.

Pickup still does not know what it grants. Configure takes a finished caption the same way it already took a finished colour, so one prefab serves every skill and the health drop alike.

The banner text and the pickup text are separate fields, because they are read at different moments. “Attack Speed Increased!” is written to fire after the fact, and reads oddly floating above something nobody has touched yet:

Why the captions are not in the world

They began as world-space text on the pickup itself. They read correctly and looked soft, and the cause was structural rather than a setting anyone had got wrong. Dumping the passes on the two renderers of one prefab shows it plainly:

Core   HDRP/Unlit                  8 passes, one of them MOTIONVECTORS
Label  TextMeshPro/Distance Field   1 pass,   LightMode ""

Text that writes no motion vectors gets reprojected by temporal antialiasing against whatever motion sits behind it — and these bob, billboard and orbit, so every frame was blended against a history taken from the wrong place. Raising the camera's TAA sharpening helps the whole image and does not fix that.

PickupLabelBoard draws them on the Screen Space Overlay canvas instead, which the UI composites after HDRP has finished its frame. It is the same property that keeps the HUD beside them sharp. The cost is bloom, which is composited before it, so an HDR face colour no longer glows by itself — the glow is TextMeshPro's own Glow feature now, in the glyph shader, needing no post-processing at all.

Screen-space text does not shrink with distance, which is the trade. A caption across the arena would otherwise announce itself as loudly as one an arm's length away, so there is a falloff: full size at 160 units, floored at 55%.

That board has a second client now. Floating combat numbers go through it rather than through a board of their own: both are one line of glowing text projected through the same camera, and a second pool would mean a second set of cloned materials to free and a second copy of the occlusion and distance rules to keep in step. The obvious alternative — world-space popups — is the exact defect described above, so it was never available.

They show experience, not damage

A floating number in a shooter is usually damage. Damage here is always exactly 1: every weapon, every enemy, the boss included — all four TakeDamage call sites pass 1. A column of ones would be thirteen hundred glyphs a run telling the player something they already know.

The reward is the number that varies. A Scout is 5 and a Fighter beside it is 15, and knowing that mid-run is what turns going after one rather than the other into a decision. The hull flash carries the other half of the message — that a shot landed, and on what — so the number is free to carry what the kill was worth rather than repeating that it happened.

Two ways to render nothing, convincingly

Enabling GLOW_ON without calling UpdateMeshPadding leaves every glyph in a quad cut for a material with no glow. The distance field saturates across the whole of it and the caption draws as a row of solid blocks — correct layout, correct colour, no letters.

And pooled pickups arrive with their mesh nulled, because TextMeshPro.OnDisable clears it. Assigning .text only queues a rebuild those objects never received, so the first working build had three correctly configured labels with zero vertices between them.

In front of the camera is not the same as visible

The volcano stands in the middle of the ring, so a pickup on the far side projects to a perfectly good screen position — straight across the cone that is hiding it. A three-way offer would routinely put one of its three names on a rock.

The test is arithmetic rather than Physics.Linecast, because the scene has no scenery colliders at all: not the island, not the ruins, not the volcano. Giving the island a MeshCollider would push 40,050 vertices of static geometry into the physics world for the first time, and bullets and enemies would then need keeping off it. That is a gameplay change to fix a caption.

It is flat because the arena is. PickupSpawner places pickups at the player's own height, and the camera holds that height and looks along the horizontal, so every sight line that matters runs level at y = 70. A cone sliced at one height is a circle, and the whole question drops to two dimensions — closest approach of the camera-to-label segment to the arena axis, clamped to the segment so a pickup in front, with the volcano behind it, is not mistaken for one hiding behind the volcano.

Ten minutes, and enough to earn across them

The pool held eight picks and the run was five minutes, so a player reached the end of their build around level nine and every level-up after that handed out a health pack. That is the shape of a game that stops rewarding you two thirds of the way through.

Doubling the timer would not have fixed it, and would have broken something else. Spawning stopped at 301 seconds, so the second half would have been empty; and raising that cutoff runs straight into the ramp, which compounds. Move Speed cannot be given to the ship alone

The one upgrade about not being hit rather than hitting harder. It raises orbiting and climbing by the same tenth, so two speeds authored equal stay equal for the whole run rather than drifting apart a pick at a time.

It also cannot be applied to the player on its own. The Main Camera runs its own PlayerMovement and holds station only because both speeds match, so the bonus is a multiplier the two of them share. Raise one without the other and the camera falls behind and the player flies out of frame — and nothing about that bug would point at an upgrade. Both axes scale safely because the camera carries ApplyBounds too and is clamped to the same vertical envelope as the ship.

Back Shot is gone. It was the one pick that changed what the gun does rather than how much of it there is, and with nineteen other picks doing the stretching it was not needed to carry the late run. Without it the backward pattern was five empty rows and the second FireLine was dead code, so both went with it.

Ending the run uses the same idea for a different reason. The boss is instantiated from a prefab mid-run, so it cannot hold a reference to anything in the scene. Rather than have it hunt for a menu by tag, it reports:

RunOutcome.ReportBossDefeated();

VictoryMenu subscribes in OnEnable and shows the panel. RunOutcome clears its subscribers on subsystem registration, because static events outlive a scene — and outlive play mode entirely when domain reload is disabled.

A Unity rule worth internalising

Nothing runs on an inactive GameObject — not Awake, not OnEnable. DeathMenu can live on the panel it shows, because Player calls it through a direct reference. VictoryMenu cannot, because it listens for an event: a component on an inactive object never subscribes. It must sit on something active, like the Canvas.

One related fix: Time.timeScale survives a scene load, and all three menus set it to 0. Restarting used to load a frozen game. MainMenu now resets it before loading.

What the run was, once it is over

Both endings used to stop time and put up a card carrying a title and two buttons, leaving a third of it empty underneath and saying nothing about how the run had gone. RunStats counts as it happens — kills, experience, level, and the picks taken — and RunSummary writes them into that gap.

Counted rather than derived, because most of it cannot be recovered afterwards: experience earned is not readable from the player's level and bar, since levels cost a different amount each time and the bar is reset on every one of them, and enemies destroyed is not readable from anything at all once they are back in the pool. The clock stops in RunOutcome.ReportRunEnded, the one place both endings already pass through — and which they reach before stopping time, so the reading is the run rather than zero. It is scaled time, so a player who spends four minutes on the pause screen has not survived four minutes.

A retry used to inherit the last run's speed

PlayerMovement.speedMultiplier is static, and deliberately so — the ship and the Main Camera both run that component, and they hold formation only because the number is shared. It carried a SubsystemRegistration reset and a comment claiming that stopped a second run starting at the speed the first one ended at. It only half did.

SubsystemRegistration fires when play mode is entered. It does not fire when the player presses Retry, because that is SceneManager.LoadScene and play mode never ended. Measured in play mode rather than argued: five Move Speed picks, then a scene load, and the multiplier read 1.5 on the other side. It compounds — retry twice and a run starts at 2.0, with the camera speeding up alongside the ship, so nothing about it looks like an upgrade bug.

The fix was to follow the pattern already in the project rather than invent one: ObjectPool and RunOutcome both pair SubsystemRegistration with a SceneManager hook, and this had only the first half.

Rendering

The presentation work was done on a branch while URP remained the shipping game. That question is now settled: the HDRP work is the project. Because the branch never diverged — it was only ever ahead — promoting it was a fast-forward rather than a merge, and nothing had to be reconciled.

The sky

HDRP ignores the legacy skybox material — sky comes from a Volume. The original starfield was six separate 4096× textures totalling 302 MB. They were baked into a single cubemap cross and imported as a cubemap texture, which drops into the normal texture pipeline: block compression, streaming, platform overrides.

The Volume's HDRI is what the camera sees. Lighting → Environment → Static Lighting Sky is what the baker sees, and it is the only thing feeding sky light into lightmaps, light probes and the probe volumes. They are set independently, and nothing warns when they disagree.

That component lives on a hidden GameObject. Delete the object and Unity recreates the component on the next scene open — empty, pointing at nothing. Which is what happened: bakes kept succeeding, took no sky light at all, and said so nowhere. The evidence was in the scene file rather than on screen, where the baked ambient probe's sh[0] had fallen from 0.0906 to 0.0715.

The fix pointed it at the scene's volume profile rather than the default one it had originally referenced. Both carry the same HDRI cubemap, but the default holds it at EV 0 while the scene shows it at EV 1 — so the bake had always been a stop darker than the runtime view, even while it was working. On the same profile now: sh[0] is 0.1343, 48% above where it started.

Cloud that drifts through the arena

HDRP's volumetric clouds cannot do this one. They refuse to render within roughly twenty units of the camera, their altitude range has a hard 100 m floor, and their noise runs at kilometre scale — measured across a 370-unit island the field is uniform, so the sky turns overcast as a whole and no cloud ever drifts past anything. ArenaCloudBank drives a Local Volumetric Fog volume instead, which is the local-scale equivalent and takes a Texture3D density mask.

The mask scrolls; the volume does not move. HDRP samples the mask in the volume's own space, so scrolling a tiling texture gives endless cloud while the box stays put — move the box instead and its edges sweep through frame once a lap. The noise has to tile for the same reason, so every octave hashes its lattice modulo its own period and the periods are powers of two that divide the resolution, which makes opposite faces line up exactly.

HDRP measures scrolling in mask-UV per second, a figure nobody can picture and one that silently changes meaning whenever the volume is resized. driftSpeed is world units per second, converted through the volume's own size and tiling, so it keeps meaning what it says.

Size and spacing were the same knob, which is why the banks packed together

The clouds themselves were right and there was no sky between them — and neither existing control could fix that, because both moved size and spacing at once. coverage raises the density threshold, which erodes every bank inward from its edges; basePeriod scales the lattice, which makes banks bigger and further apart. Each buys open sky by changing the clouds you wanted to keep.

A second, much slower field now decides which patches of the tile hold cloud at all. Inside a kept patch the threshold is untouched, so those banks are exactly the ones that were already there; the cleared patches simply go empty. The cut is taken as a percentile of that field rather than as a fixed value, so sparsity keeps its meaning across seeds and periods — the same reason the main field is normalised before coverage is applied to it.

The lava shader

LavaFlow samples a seamless noise texture with triplanar projection — three world-space planar projections blended by the surface normal. That ignores the mesh's UVs entirely, which matters because the island's UVs are badly stretched and because a single projection collapses into stripes on flat surfaces.

Two layers scroll at different speeds. Where they slide across each other, brightness shifts — that reads as molten flow, whereas one scrolling layer just looks like a texture sliding past.

The structural insight came late and was the one that made it work:

veins    = saturate(n1 * n2 * contrast);
baseColor = crust;                      // never lerped
emission  = hot * glow * veins;

Base Colour stays solid. Only emission is modulated. Lerping both — the earlier approach — flattened the low-poly faceting into a glowing silhouette.

Lighting is physical

The single most useful HDRP fact here

HDRP works in real units. Emission is in nits, exposure in EV100. At EV 10 mid-grey sits near 128 nits, so lava glowing at 1.5 is invisible while 1000 is correct — real lava is roughly 1500–3000 cd/m². Values that look absurd next to URP's unitless multipliers are often simply right.

Emissive surfaces cannot cast shadows — shadows are rendered from a light's point of view, and an emissive material isn't a light. The lava's glow on surrounding rock comes from real area lights placed on the emitting surface.

Bullet lights, and one shadow per volley

With maximum skills the player has ~36 bullets alive; the boss adds ~174. A light each is impossible — every shadow-casting point light renders the scene six times into a cubemap. BulletLightPool keeps ten lights that follow the bullets nearest the camera, and only a few of those cast shadows. It clones a template light you configure in the Inspector, so it carries no HDRP dependency and would work unchanged on URP.

Which few was the expensive question, and distance was the wrong answer. A volley is not a loose group that drifts apart. FireLine stacks its bullets up the pivot, and every one of them orbits the same centre at the same angular speed at its own fixed height — so at full Shot Upgrade the six bullets are a rigid column about twenty units tall for the whole of their flight, offsets of 0.5, 1.5 and 2.5 either way against a shotSpacing of 4. Each carries a light of range 100. Six lights of range a hundred strung up twenty units cover very nearly the same ground.

Picking casters by distance chose exactly those six, because the bullets nearest the camera are overwhelmingly the newest volley. So the shadow cost scaled with Shot Upgrade: the pick that makes the gun feel good was the pick that made the frame expensive. Casters are now chosen one per volley, nearest first.

The saving grows with the upgrade

More shots per volley means fewer distinct volleys among the lit bullets, so the shadows get cheaper as the gun gets better. Ten lit bullets spanned two volleys and drew two shadows, stable across six consecutive frames.

That inverts where the risk lives. shadowCastingCount now means at most how many volleys, and the expensive case is the opening minute: with single-shot volleys, ten lit bullets are ten separate volleys. The budget is what protects the start of a run, where it used to be what protected the end.

The shadows were fine. The camera was too far away to be shown them.

Bullet shadows stopped appearing in play mode — visible in the scene view, visible if you paused and flew the camera in close, absent from the game view. Nothing in BulletLightPool was wrong, and nothing in the light template was wrong. The cause was one number in GraphicsDirector: a runtime Volume override pinning maxShadowDistance to 60, with a comment sizing it against an arena 27.4 units across.

That comment had been right. The arena is ten times that now, and the camera trails at radius 212 — so every shadow in the scene was being culled by distance long before it reached the frame. It is 500 today. A stale world-unit constant does not announce itself after a rescale, because the code still compiles, the setting still applies, and the effect it kills is one you have to be looking for.

An audit of the rest of GraphicsDirector found this was the only world-unit number in its 1,225 lines, and the only runtime volume override in the project. That last part is why no search of the .asset files could ever have found it: the override does not exist on disk. It is built in C# at runtime.

Reading the shadow atlas as numbers rather than as a picture

HDRP ships an atlas debug overlay, and on this scene it could not be made to render legibly for the punctual or area atlases — every mode, range sweep and single-light view came back black. GraphicsStateReport now prints the occupancy instead: per light, its resolution, its face count, and what share of its atlas it holds. Cost is the same model HDRP uses — a point light is six faces of resolution squared, spot and area are one, directional is one per cascade.

Two facts surfaced immediately that no overlay would have offered. The scene's single area light fills its entire atlas at 4096² — 100.0% of the area map, on its own. And play mode runs the High tier rather than Ultra, because the director applies the saved quality level at startup, so the atlas being filled is the 4096 one and not Ultra's 8192.

The same tool had been quietly lying about something else. It read VolumeManager.instance.stack — the default global stack — and reported maxShadowDistance as 500 while the camera was rendering with 60. HDRP evaluates volumes per camera, against that camera's layer mask, position and anchor override, so a runtime-created volume can be absent from the global stack entirely. It resolves a stack for the actual camera now. It was proven by stamping a sentinel: the old path read 500 where the new one read the 123 that had just been written.

Exposure, and one lever for fog

Exposure is fixed at −0.1 rather than automatic. Automatic hunts: the lava fills a large part of the frame and its share of it changes as the camera orbits, so the whole image breathes in response to set dressing. Fixing it also makes the auto-exposure limits inert, which retires a pair of numbers that only mattered while something was reading them.

The fog had five overrides disagreeing about the same effect — colour mode, colour, maximum distance, base height and maximum height all pinned at once. Those are back on their defaults, leaving meanFreePath, brought from 300 to 50, as the single control over how thick the air is.

On the top tier — the one called Ultra since the split — probe volumes moved from L1 to L2 spherical harmonics, the cookie atlas to 4096, the area shadow atlas from 4096 to 8192, and area shadow filtering up a step. The lighter High inserted beneath it kept Medium's probe volumes and took 2048 instead. Sky reflection was left at 2048 on both. Two lights stopped culling shadow casters against the view frustum, so geometry outside the frame keeps throwing shadows into it.

The interface

The UI was rebuilt from nothing. Three separate problems were wearing one coat, and only one of them was about taste.

Why it looked low resolution

Both canvases were set to Constant Pixel Size — a mode in which the reference resolution is ignored entirely. The 800 × 600 sitting in the scene had never done anything. The interface simply never scaled, so it shrank on every display better than the one it was authored on. Underneath that, the source art was genuinely small (skillSlot.png was 48×49) and eleven elements used Unity's built-in default sprites — the grey rounded rectangles every prototype ships with.

No bitmap art at all

Rather than redraw those sprites, the interface is drawn by two shaders using signed distance fields: chamfered frames, corner brackets, drifting scanlines, edge glow. Nothing samples a texture, so nothing can go soft — every edge is evaluated per pixel at whatever resolution the display happens to be.

The piece that makes it hold together is small and easy to miss. HoloRectData writes each element's pixel size into the mesh's second UV channel, and the shaders work in pixels rather than UV:

float2 p     = (i.uv - 0.5) * size;   // pixels from centre
float  d     = HoloChamferBox(p, inner, _Chamfer);
float  edge  = HoloBand(d, _Border);

Without it the shaders could only work in UV space, and every measurement — corner cut, border width, bracket length — would stretch with the element. A wide health bar and a square skill slot would not look like parts of the same machine. The canvas has to list TexCoord1 in its additional shader channels or the data never reaches the GPU, so the component says so rather than failing silently.

Bars that show what was lost

The old bars snapped, so losing health produced a bar that was merely shorter next time you looked. BarMotion drives a second value that lags behind the first: a hit leaves a red stretch that holds for ~0.45 s and then drains. It is a pure class, so the cases that fail invisibly are covered by tests — a trail appearing while healing, or one that never drains and leaves the bar looking permanently damaged.

The bar also flinches now, six pixels on a shrinking circle over 0.22 s. The roadmap asked for a screen shake; the bar is the better trade in a game whose camera is already orbiting, because a screen shake says something happened somewhere and this says what happened and where to look. It also needs no accessibility switch of its own, which a full-screen shake would.

Two details that decide whether it works

Damage is worked out from the value rather than asked of the caller. Player.Heal and the Max Health skill both arrive through the same SetHealth, and a bar that flinches when the player is healed says the opposite of what happened.

The resting position is captured at Awake, not when a shake begins — hits land close together late in a run, and a second one starting inside the first would record the thrown position as home and walk the bar out of its corner a few pixels per hit. The flinch runs on unscaled time for a reason specific to it: the hit that kills runs SetHealth and then stops time in the same frame, so on scaled time the bar would freeze mid-throw behind the death screen.

One screen at a time

The first version let the options screen open on top of the pause screen — two dimming scrims and two panels stacked. The rule is now enforced in MenuScreen.OnEnable rather than by the buttons, because the buttons are not the only thing that opens a screen: DeathMenu, PauseMenu and VictoryMenu all call SetActive directly. Anything that shows a screen, by any route, now closes the rest.

Escape walks back the way you came

PauseMenu.Resume hid exactly two GameObjects: the pause panel and the options hub. Those were the only screens that existed when it was written, so once Audio, Display and Graphics arrived, pressing Escape three screens deep restarted the game with a settings panel still on screen.

Escape now steps back one screen per press and only resumes once there is nothing left to back out of. Each screen carries a previous link to the one it was opened from; MenuScreen.Back() follows it and reports false at the root, which is the pause menu's cue to resume. The screens close before timeScale returns to 1, so play can never restart underneath a panel.

Why a link rather than a list

The obvious repair was to add the three new screens to the list Resume already hid. That fixes today and rebuilds the same trap for whoever adds the fourth. The previous link is set by the menu builder in the same call that wires each Back button, so the key and the button read one source and cannot drift apart — and closing everything is a sweep over every MenuScreen in the scene, which cannot fall behind the screens that exist.

A title screen is not a dialog

The main menu was first built the same way as the pause menu — a centred, framed panel — and it covered the logo the title video renders, while printing a second copy of the game's name underneath it. It is now a column of entries in the lower left with no panel and no title text, which is the usual arrangement precisely because it leaves the key art as the thing being looked at.

The two button styles react in their own language. Title entries slide, because they have no frame; framed buttons lift their edge glow, extend their corner brackets and run a light up the panel. Unity's colour tint is not used for either — it fades the whole image at once, including the fill, which flattens a frame instead of sharpening it, and it cannot reach a shader property at all.

Generated, not placed

Four editor tools build the HUD, the in-game menus, the title screen and the video output, over a shared factory. The interface is defined by numbers, and numbers belong in a file that can be re-run — nudging thirty rect transforms by hand and hoping they still line up at another aspect ratio is how the original ended up as it did.

The tools are additive and fully undoable, and they solve the same problem three times: several gameplay scripts lived on the objects being replaced. HealthBar sat on the object called "HealthBar", ExpBar on "XpBar", MainMenu on "MenuPrincipal". Each tool recreates the component on the new element and repoints everything holding a reference to it before destroying the original.

Identify by reference, not by name

The menu builder finds the old screens by asking PauseMenu.pauseMenuUI, DeathMenu.deathMenuUI and the rest what they point at, rather than matching names. Names drift and get duplicated; pauseMenuUI is the pause screen by definition. Only the leftover sweep — for objects a previous run already orphaned — has to fall back to names.

A slider that cannot be dragged

The bars are drawn entirely by the shader, so the volume sliders were built without a fill rect or a handle — both looked redundant. They were inert. Unity's Slider.UpdateDrag maps the pointer through handleRect.parent, falling back to fillRect.parent, and with neither assigned it returns before touching the value:

RectTransform clickRect = m_HandleContainerRect ?? m_FillContainerRect;
if (clickRect != null && clickRect.rect.size[(int)axis] > 0) { /* only here */ }

The control still looked and reported as if it worked. Each volume slider now carries an invisible handle purely for hit-testing; the bar shader's leading edge remains the only thing drawn. The HUD bars never needed one, because nothing drags them.

It never depended on the pipeline

Screen Space Overlay canvases render outside the SRP entirely, so the UI shaders behave identically under HDRP and URP. The tools sit in their own editor assembly for the same reason — the other editor tools reference HDRP, and keeping the two apart meant the interface was never tied to that choice. With HDRP now the project this buys nothing today, but the separation cost nothing to maintain and the alternative would have been unpickable.

That property also fixed the title video. Drawn on the camera's far plane it became scene content, so HDRP exposed and tonemapped it with an exposure tuned for a lava-lit volcano, and it came out dark. Routed through the overlay canvas instead, nothing touches it.

Two settings that only work together

The video also looked crunched in-game but correct in a media player. Its render texture was ARGB2101010 with sRGB off, in a Linear-colour-space project: the video's sRGB-encoded pixels were stored and read as though already linear, then encoded again on output. That extra gamma lifts and stretches the dark end — exactly where a compressed video keeps its quantisation steps — dragging block artifacts into view.

Ticking sRGB alone does nothing, because ARGB2101010 has no sRGB variant in the graphics APIs. The format has to drop to ARGB32 for the flag to apply. Counter-intuitively 8 bits read correctly beats 10 bits read wrongly: the source is 8-bit anyway, and sRGB spends its precision where the eye is sensitive.

Audio

Before this there was one AudioSource per scene and no code at all — no way to play a sound, and a volume slider on the options screen with no listeners attached to it, so moving it did nothing.

Four channels

Master, Music, Effects and Interface. Interface is separate from Effects deliberately: turning combat sound down should not make the menus feel broken, and menu sounds have to be audible while timeScale is zero. The labels are written for players rather than for the mixer — "Effects" says what is being turned down, "SFX" says how the code is organised.

AudioDirector creates itself before the first scene loads and survives scene changes, so a level set on the title screen is still in force in the game. The old per-scene slider could not have carried a setting anywhere even if it had been wired.

Why there is a voice pool

Everything about playback follows from one fact: the player fires up to ten projectiles per volley and the boss twenty-nine. A clip per shot would mean hundreds of AudioSources, and every copy starting in the same frame adds amplitude until the mix clips.

So there are 24 pooled voices, and every SoundDefinition carries a minimum retrigger interval and a maximum concurrent voice count. Thirty bullets leaving together produce one shot. When every voice is busy, new requests are dropped rather than queued — a late sound is worse than a missing one.

Sounds also hold several clips and a pitch range, and the clip picker chooses from the others rather than at random, because plain randomness produces audible repeats far more often than people expect.

What actually makes a sound

Eleven call sites, and they answer to one asset rather than to a field on each script. Wiring them individually would have meant editing the player prefab, the boss prefab, every button and every menu — and an unassigned field on any one of them is a silence nobody notices.

Per-enemy death sounds are the deliberate exception to the one-asset rule: they live on EnemyDefinition beside that enemy's health and reward, because they vary per enemy and that asset already existed.

The two vendors order their quality enums backwards

Not an audio problem, but the same shape and worth stating once: NVIDIA.DLSSQuality runs cheapest-first, AMD.FSR2Quality runs best-first. A straight cast hands the player who picked Quality the fastest, ugliest mode — and it still renders, still upscales, and still reports the setting they chose. Anything that maps a player's choice onto a vendor enum is worth writing out explicitly and testing.

Filling the clips

Two editor tools, because a correctly wired silent call site and a broken one look identical. Generate Placeholder SFX implements DrPetter's sfxr as synthesis — the classic generators, deterministic from a seed, writing mono 16-bit WAVs and assigning them. That proved every call site fired before a single audio file had been sourced. Report Silent Sounds lists anything still without a clip, because a SoundDefinition with an empty clip list is dropped silently, which is correct behaviour and completely invisible.

The placeholders were later replaced with Kenney and Sonniss material. Both tools remain: one is the fallback, the other is the check.

Measuring loudness rather than guessing it

The per-sound levels were chosen while every clip was generated and peak-normalised, so they were pure attenuations of a known starting point. Clips from a pack share no such starting point — the same 0.7 that was a deliberate step down for one became most of the reason another was inaudible. A number tuned against an assumption that has since changed is worse than no number.

Balance Sound Levels now measures gated RMS on every clip and writes level-corrected copies at a common target, peak-limited so nothing clips. Gated, because a plain average makes anything with a long tail read as quiet — which is most explosions, the exact sounds that were reported as too soft. The files carry the matching; the volume field carries only intent, which is now a short table of how much quieter a sound should be because of how often it fires.

One trap on the way: GetData returns silence rather than failing for a clip that is still compressed, so the tool forces DecompressOnLoad around each read. Measuring zeros and calling it quiet would have been the worst possible outcome.

The volume curve

Hearing is logarithmic, so a slider driving amplitude directly does almost nothing over its bottom half. AudioLevels is pure and tested; the value it exists to prevent is negative infinity, which log10(0) produces and which permanently poisons any mixer parameter it reaches.

ToDecibels(1.0)  =   0 dB
ToDecibels(0.5)  =  -6.02 dB
ToDecibels(0.0)  = -80 dB     // floored, never -Infinity

Music takes the other path

Music does not go through the voice pool — those voices are short and recycled, so a looping track would either hold one forever or be cut off mid-bar when the pool ran dry during a firefight. It gets its own AudioSource, marked with MusicSource, which treats the level authored on the source as the balance and lets the slider scale it. With Music at full the game sounds exactly as the team mixed it.

No AudioMixer is required. Mixer assets cannot be created through Unity's public API, so depending on one would have meant a manual setup step before any sound worked at all; instead each sound has an optional mixer group, and adding a mixer later for effects or ducking is a per-asset field rather than a rewrite.

Where three rounds of silence actually went

Unity 6 renamed the AudioSource's Audio Clip field to Audio Generator, and serialises it as m_Resource alongside the legacy m_audioClip. Asked whether the music went "in the audio generator", the answer given was no — read as a question about the Sound asset system rather than about the field on the component. The clip slot stayed empty and nothing played.

A second failure compounded it: the scene files were read from disk while the editor held unsaved changes, so the analysis described the last-saved state rather than the live one. MusicSource now logs a warning naming the object when it has no track, instead of presenting as silence with nothing to look at.

Performance and diagnostics

The profiler said there was no throughput problem: 183 FPS, 5.5 ms of frame time against a 16.7 ms budget, 4.1 ms on the GPU, 564 draw calls of which 530 were instanced. GPU instancing was already active through the SRP Batcher and would have added nothing.

The one real signal was a regular spike toward 33 ms, spaced to track the spawn and fire intervals. A hitch is more perceptible than a lower steady frame rate, which is the whole reason the pooling work happened — not to raise the average, but to flatten those.

Pooling

Projectiles, hit effects, pickups and — since a later pass — enemies are all reused instead of allocated. Despawn destroys anything the pool did not create, so it is safe to call on anything.

Enemies were excluded on a number that expired

The original rule was that enemies spawn "once or twice a second", so there was nothing to win against the risk of resetting their state. Measured against the wave asset with the real interval maths, the first half of that only holds early — nineteen streams each ramp their own interval and the curve compounds:

Which is also the stretch with the most bullets, effects and lights competing for the frame. They were the last thing in the game still going through Instantiate and Destroy.

The second half of the rule was accurate, and named the exact three things that needed handling. Health rebuilds in OnEnable — left in Awake a reused enemy comes back holding the health it died on, which is zero. Enemy_1 cancels its firing invoke before re-arming it, or repeats stack and an enemy fires faster the more times it has been recycled. And EnemyMovement restores the direction its prefab was authored with: leftOrRight is written at runtime by ColliderScript when the player crosses a trigger, so a reused enemy would otherwise set off whichever way it was last turned — with nothing about the symptom pointing at a trigger volume.

Reuse means Awake and Start no longer run per spawn, and two scripts depended on that:

  • ShootScript reset its rotation in Start — a reused bullet would have kept whatever rotation it died with. The Scenario lookup is now cached statically too; it was a tag search per projectile, and reuse would have repeated it forever.
  • DestroyAfterTime armed in Awake — a reused projectile would have flown on forever. Moving it to OnEnable is only half the fix: OnDisable has to cancel, or a projectile that dies early carries a pending timer into its next life and vanishes partway through it.
One deliberate behaviour change

Destroy is deferred to the end of the frame, so a bullet's collider stayed live after impact and could damage two overlapping enemies in the same frame. Despawn deactivates immediately, so a bullet now hits exactly one target. That piercing was almost certainly unintended, but it is a real change in dense waves.

Reuse is a teleport, and the renderer reports it as movement

A pooled object is moved to its new spawn point and switched back on. On its first frame the renderer therefore reports motion from wherever it last died — often right across the screen. Anything that reprojects the previous frame using motion vectors drags the old image along that path: FSR2 left visible ghost trails on the explosion particles, and TAA smeared more subtly. It happens constantly, at five volleys a second.

Motion is now suppressed for exactly one frame after reuse and then restored, because after that the object is moving normally and its motion vectors are worth having. The restore is done by a single component on the pool's root rather than a callback on each instance — at peak there are around 200 projectiles alive, and 200 per-frame callbacks to undo a flag is the cost the pool exists to avoid.

The player and the boss build their pools up front. The boss sizes its own from its pivot count — an attack fires one projectile per pivot, so the pivots already say how many — and warms one volley per travel direction rather than the six its projectile lifetime implies, so its entrance does not stall to build a pool it will fill anyway.

The performance overlay

A build sent to a tester needs to report its own numbers, because a tester cannot run a profiler. PerformanceOverlay creates itself, works in a normal non-development build, hides behind F3, and exports its report to the clipboard and a file on F4 so results can be pasted back rather than transcribed from a screenshot.

It leads with the 1% and 0.1% lows rather than average frame rate. An average cannot show a stutter, which is the thing worth measuring after pooling; the lows can.

Not everything asked of it is obtainable, and the gaps are reported as gaps. GPU utilisation as a percentage is not exposed by any API, so it reports GPU frame time instead — which also distinguishes a GPU-bound machine from a CPU-bound one. Live VRAM comes from ProfilerRecorder, trying both counter names Unity has used, and process CPU from System.Diagnostics.Process, which some scripting backends refuse. All of it degrades to n/a rather than zero: a confident zero in a performance report sends someone chasing a problem that is not there.

The graphics summary omits shadow and anti-aliasing settings on purpose. Under a scriptable pipeline those come from the pipeline asset and the QualitySettings values sit unused, so printing them would look authoritative and be wrong.

What a tester's report has to answer

A real report came back from a weak machine and could not answer the first question anyone would ask of it. It said the window was 1280×720 — but not what the game had actually rendered at, and not which upscaler was running. "Slow at native" and "slow even with FSR Performance" are different problems with different answers, and the report could not tell them apart. Both lines exist now.

The overlay reads its own numbers

That same report showed 20 FPS with frame times of 49.8 ms and 100.0 ms on a 60 Hz screen — exactly 3 and 6 refresh intervals. That is not a slow machine, it is VSync rounding the frame rate down to 60/3, and the GPU was finishing in 39.9 ms with time to spare. The overlay now spots that pattern itself and prints what turning VSync off would give, because a tester cannot be expected to notice that their frame time is an integer multiple of anything.

It only fires when the GPU is measurably finishing sooner. A machine genuinely at its limit is not being held back by anything, and saying so would be noise.

The render-resolution line reports what was asked for and appends what the pipeline resolved only when the two disagree. HDRP recomputes its scale only when the active camera changes, which in a single-camera build can leave the resolved figure stale — so a mismatch between the two numbers is itself the diagnosis, where a single figure would just be quietly wrong.

That last figure retired a whole line of enquiry at the time. Enemies were then the one unpooled spawn path, and the obvious suspicion was that their churn caused the hitches. The capture says the collector never ran, so pooling them would not have fixed a single spike.

They were pooled later anyway, and the profiler did not ask for it

Worth being straight about, because the two pieces of evidence answer different questions. What changed was not the frame data but the stated reason for the exclusion — "once or twice a second" — which measurement showed holds only for the first half of a run and is wrong by roughly four times at the five-minute mark.

Whether that costs anything at 7.55 spawns a second is unmeasured. The capture above is the only evidence either way and it does not record how far into a run it was taken, so it cannot settle the late-game case it would need to. The change bought consistency and a corrected comment. It has not been shown to buy frames, and the honest next step is a capture at t≈280 rather than an assumption in either direction.

The instrument was the hitch

The captures showed a rhythmic 15–18 ms spike every ~105 frames — about 0.55 s, like clockwork, in an otherwise 2 ms frame. Autocorrelation of the CPU series peaked hard at lag 105 with a clean harmonic at 209, which is the signature of something on a fixed timer rather than of garbage or load.

It was PerformanceOverlay. It sampled WorkingSet64 and TotalProcessorTime every 0.25 s, and both go through Process.Refresh(), which on Windows re-reads the OS process table system-wide rather than looking at our own block. It costs milliseconds. At ~4.5 ms a frame the refresh landed every ~56 frames and stalled on every other one — the OS caching the result in between — which is where 105 comes from.

Three captures settled it. Autocorrelation at lags 104–111 read 0.176 with the overlay shown and −0.012 to −0.003 with it hidden: not a reduction, an erasure. The process counters now sample on their own two-second cadence while the frame timings stay at a quarter second, because those come from a Unity-side ring buffer and are genuinely cheap. Resident memory does not move meaningfully in 250 ms, so nothing readable was lost.

The spikes that survive are all in the render pipeline, never in gameplay. On a spike frame RenderShadowMaps goes from ~0.6 ms to 8.4 ms and CreateResourceWithTag from 0.66 ms to 4.4 ms — allocation plus a full re-render, which is the signature of a shadow map being created from scratch rather than merely redrawn. The suspect was BulletLightPool, and measuring it found something larger than a toggle. The scene ran five shadow casters where the code defaults to one, all of them chasing the same newest volley, and each cost about 159k triangles and 85 draw calls a frame. At three casters they were already 70% of all geometry submitted. That is now one per volley, which is documented with its numbers under Rendering.

What that does not yet prove is the millisecond. The measurement is submitted work — draw calls and triangles — taken in the editor on a paused frame, with GPU timing unavailable. It shows the mechanism is real and large. Attributing the 8.4 ms to it still wants a capture from a real run.

Worth keeping in proportion

These spikes are ~15 ms against a 16.67 ms budget at 60 FPS. They are visible because the game runs at 200 + FPS, where a 15 ms frame is a three-frame drop. Shipped at 60 they would fit inside the budget and vanish. That does not make them not worth fixing, but it does make this a polish problem on an already-fast game rather than a performance problem.

Quality presets and settings

Six levels sharing one asset, then eight generated ones, now four — three of Unity's own and one hand-authored

The jam project had six named quality levels and a single HDRenderPipelineAsset shared between them — renderPipeline: did not appear in QualitySettings.asset at all. Under HDRP the shadows, the atlases and every support flag live in the pipeline asset, so switching from Very Low to Ultra changed almost nothing. A quality dropdown built on that would have been another control that looks functional and does nothing.

The answer was a builder tool that generated eight assets from tables written in C#. It worked, and it was wrong in a way worth recording: the numbers were invented here rather than measured anywhere. A flat 512 reflection cache failed its allocation every frame and logged so forever; ray-traced global illumination on the top two tiers rendered every dynamic object as a black silhouette. Both took a build to find, and neither was a coding error — they were confident numbers nobody had grounds for.

So the tool is gone. HdrpQualityPresetBuilder, PipelineTuning, the eight generated assets and the Custom quality level are all deleted, and nothing in the project writes a pipeline asset any more. Three of the four quality levels are copies of the assets Unity ships with a new HDRP project — Performant, Balanced and High Fidelity, renamed Low, Medium and Ultra — tuned by hand in the Inspector afterwards. Unity keeps its own tiers self-consistent; this file no longer has an opinion about atlas sizes.

High is the exception, and the newest tier. It is a copy of High Fidelity stepped down where the cost sits rather than where the feature list does: both it and Ultra compile SSR, SSR on transparents, SSGI, volumetrics, volumetric clouds and ray tracing, and what separates them is budget — a 4096 area shadow atlas against 8192, probe volumes at L1 against L2, and the cookie atlas at 2048 against 4096. Sky reflection is not one of them — both sit at 2048. None of that is a volume override, which is why the two rows in GraphicsPresets are nearly identical. The tier does the work, not the table.

The default was Ultra, and three things said so

The settings screen had said Medium was the default since the tiers were rebuilt. Nothing read it. GraphicsPresets.DefaultIndex = 1, the constant whose summary names Medium, was referenced nowhere in the project; the tier actually came from ProjectSettings, which still held Standalone: 6 — an index minted when there were eight generated levels, against a list that has four.

An index past the end of that list resolves to the last entry rather than failing, so 6 quietly meant "the most expensive tier there is" and a fresh install booted on Ultra. Nothing reported it, because 6 is not an error — it is an index that used to mean something else. A constant nothing reads records an intention; it does not enforce one. The fallback now comes from the constant, and the eighteen platform entries are corrected to agree.

One thing the compile gates decide on their own: volumetric clouds first appear at High. Medium's asset ships supportVolumetricClouds: false, the same kind of hard gate as supportSSR on Low, so clouds have no row and simply arrive with the tier.

The copies sit at the top of Settings/Quality/ rather than being referenced where they were found, because a folder named Editor is excluded from player builds — a quality level pointing at an asset that never reaches the build has no render pipeline at runtime.

The originals were kept in Quality/Editor/ as untouched masters to duplicate from when a fourth tier was wanted. The fourth tier was duplicated, and the masters stayed for a while afterwards doing nothing. They are deleted now: eight assets with no inbound reference from anywhere, verified as a closed island whose only internal links were its own dead HDRenderPipelineGlobalSettings pointing at its own two profiles.

233 KB was the least of it

What they actually cost was legibility. They were named Performant, Balanced and High Fidelity — the exact pre-rename names of the live Low, Medium and Ultra — so Settings/Quality/ listed seven tier assets where four were real, and three of the seven wore the old names of the other four. On a project that had just spent a session working out which tier was actually live, that is a trap laid for the next person to ask.

The bottom two tiers have no dynamic shadows

This started as a request: rather than have the lowest tier do nothing, let it turn dynamic shadows off — the bullet lights being the obvious candidate. It is live, and it is two tiers rather than one. QualitySettings.shadows is Disable on Low and Medium and All on High and Ultra.

Medium is the default tier, which makes this more than a bottom-end concession. The Rendering section spends a good many words measuring what bullet-light shadows cost and what one-per-volley saved; on the tier a fresh install boots into, that whole mechanism is switched off before it starts. BulletLightPool.ShadowBudget returns 0 and no light is ever marked a caster.

Why the switch is in QualitySettings and not in the pipeline asset

The obvious place to express "no shadows" is HDRP's own shadow budget, and the obvious value is zero. Never set maxShadowRequests to 0. It has half a path. HDShadowManager.InitShadowManager does check for zero — and returns before allocating its atlas. GetUnmanageDataForShadowRequestJobs then dereferences that atlas with no guard of its own, so the tier threw a NullReferenceException every frame and the game drew nothing at all. The give-away sits one method below: Clear() guards with if (m_MaxShadowRequests == 0) return;. HDRP knows the state exists; one path forgets to check. All four tiers ship maxShadowRequests: 128 today.

QualitySettings.shadows carries the intent instead, and the reason it works is that HDRP does not read it for its own rendering. A field the pipeline ignores cannot break the pipeline, and it lets BulletLightPool ask the question without knowing that HDRP exists — the same pool would work unchanged on URP. The cost of a setting nothing reads is usually that it does nothing; here it is exactly what makes it safe.

The player is told. The Quality row carries "Dynamic shadows are off at this level", asked of QualitySettings rather than compared against index 0 — because it is two tiers now rather than one, and a tier inserted below would have moved the answer again. That has already happened once to this project, which is the whole argument for reading state instead of counting it.

What the tiers are not asked to do

Two things deliberately stayed out of the assets. The GPU Resident Drawer is disabled on all four, though Unity's tiers enable it: it moves draw submission onto the GPU for scenes pushing thousands of renderers, and this arena has 89 static mesh renderers and 125k vertices, with the enemies and bullets pooled and dynamic so they would stay on the normal path regardless. It also requires every BatchRendererGroup shader variant to be kept, which is a cost paid by every build for a path nothing here uses — and which surfaced as a compile warning from inside Unity's own DebugOccluder shader.

And screen-space shadows stay off everywhere. That flag allocates the buffer ray-traced shadows write into; HDRP delivers those per light, from HDAdditionalLightData.useRayTracedShadows, which is false on all four lights in the scene. Setting the pipeline flag alone allocated a buffer nothing wrote to — no effect in the editor, haze in a build.

The settings menu

GraphicsDirector is the same shape as AudioDirector: it creates itself, survives scene loads, and persists every choice. Effect rows go through a Volume it owns at priority 10000, because overriding is the only way to force an effect off — disabling a component on a lower-priority volume simply loses to whatever the scene authored.

Two rows that could not do anything, in either position

The director used to only ever subtract: it overrode a setting when the player turned it off and stood aside when they turned it on, so the on-state came from whatever the scene authored. That is a reasonable rule and it needs something underneath to author the effect on. Nothing did.

The scene authored ScreenSpaceReflection.enabled = 0, and the default profile authored AmbientOcclusion.intensity = 0. So Reflections and Ambient Occlusion each resolved to the same nothing in both positions — two controls that looked live, accepted the click, and could not change a pixel. The director is authoritative now. It still leaves intensity alone where an effect is on: quality is how much work the effect does, and how strong it looks is an authored value a settings menu has no business replacing.

Every effect is a ladder, not a switch

Each row runs Off · Low · Medium · High, and the effects with a ray-traced form continue RT Low · RT Medium · RT High on the same ladder rather than in a second row. It is one continuous cost curve and ray tracing is simply the expensive end — which also removes the state where a player holds both a screen-space and a ray-traced setting and has to work out which one the renderer used. Why no tier turns global illumination on

GI is not an addition here, it is a replacement. This scene's indirect light is baked into lightmaps and probe volumes, carefully enough that a single bake costs tens of megabytes of LFS quota. Switching GI on hands that job to a solver that has never seen the bake, and dynamic objects lose their indirect light entirely — the ships render as black silhouettes against terrain that kept its lightmap.

That shipped in a build. It read as the shadow rows being broken, because the change that exposed it was a shadow setting; the actual cause was ray-traced GI arriving on by default at the top two presets. The row is still there and still reachable — deliberately, because absent is not the same as declined — and no tier selects it.

Motion blur sits outside all of this. It is taste rather than fidelity: players turn it off on hardware that could run it at maximum, and a tier stamping over that every time quality changes would be the settings screen arguing with them. Picking a tier clears every other row so they fall back to it; motion blur's key is the one deliberately left out of that list.

What went with the Custom preset

Changing a row used to move the selection onto a real eighth quality level called Custom, backed by an Instantiate() clone of whichever preset asset it rested on. Three defects lived in that design and all three are now unreachable, which is the clearest argument for the simpler arrangement.

The clone was written into QualitySettings.renderPipeline, a persistent project setting, so a later rebuild destroyed it and left the level pointing at a dead object for the next SetQualityLevel to adopt. Rebuilding by instantiating a fresh asset meant destroying the outgoing one while HDRP's teardown of it was still in flight — fourteen to sixteen "referenced script is missing" warnings per row change, measured by bisection rather than guessed at: swapping without the destroy produced none, the destroy alone produced them every time. And the rebuild hitched hard enough to need debouncing.

Rows are a Volume overlay on the chosen tier now. Nothing is cloned, so none of it can recur. The cost is that the Quality row no longer signals that you have deviated from the tier — it names which asset is loaded, which stays true, and says nothing about the rows underneath.

Options is a hub of three screens rather than one screen of settings. Four sliders, two columns of cyclers and one column of switches want incompatible layouts, and sharing a panel meant at least one of them was always the wrong shape. Upscaling is three rows, not one list

The first attempt was a single nine-item cycler — Off, SMAA, TAA, FSR Quality, FSR Balanced, FSR Performance, DLSS Quality… — which conflated which reconstruction runs with how hard it pushes. Comparing FSR Balanced against DLSS Balanced meant scrolling between two unrelated entries. It is now Upscale Method, Upscale Quality and Anti-Aliasing as separate rows, each of which goes quiet with a note when another owns it.

DLAA belongs to anti-aliasing, not to upscaling: it is DLSS rendering at full resolution, spending its budget on edges instead of reconstruction. It makes the image cost more, not less. There is deliberately no FSR counterpart beside it — Unity's AMD.FSR2Quality has only Quality, Balanced, Performance and UltraPerformance, with no native-resolution mode to expose.

The two vendors order their quality enums backwards from each other

NVIDIA.DLSSQuality runs cheapest-first — MaximumPerformance is 0 and MaximumQuality is 2. AMD.FSR2Quality runs best-first — Quality is 0. Casting the player's choice straight across hands anyone picking Quality on an NVIDIA card the fastest, ugliest mode instead.

Nothing about that failure announces itself: it still renders, still upscales, still reports the setting the player chose. The mapping is written out explicitly in DisplayOptions — including the FSR side, which happens to be the identity and is spelled out anyway so the next person cannot assume the same of the other.

Nothing writes to the pipeline asset

The display controls apply through per-camera fields on HDAdditionalCameraData — allowDynamicResolution, the two allow… upscaler flags, the …UseCustomQualitySettings and …Quality pairs, and antialiasing. The effect rows apply through the Volume. The same settings exist on the pipeline asset and would have been the shorter route for both.

They are not used because asset changes made in play mode are not rolled back when play mode ends. Unity reverts scene changes; ScriptableObject edits persist and get written on the next save. A settings menu that wrote there would let one slider drag in the editor permanently rewrite the project's shipped defaults — and it would only misbehave on the developer's machine, since a built player never serialises the asset back. Correct in the build, quietly corrupting in the editor, is the worst shape a bug can have.

That rule used to have one exception: the rows needing pipeline fields wrote to a runtime clone. Removing the generated presets removed the exception with it, so the heading is now literal rather than nearly true — no code path in the project writes a RenderPipelineSettings field at all.

Availability comes from HDDynamicResolutionPlatformCapabilities.DLSSDetected and .FSR2Detected intersected with the asset's own upscaler list, so an upscaler the machine cannot run — or that the tier does not permit — is left out of the cycle rather than offered and refused.

Sharpness is the one slider

Every other graphics row is a cycler. Sharpness is not, and the reason the rule exists is the reason it does not apply here: cyclers step because settings have performance cliffs — render scale moves in tens because 73% is not a choice anybody means to make. Sharpening costs the same at every value, so every position is a real choice and a slider is the honest control.

It drives three things at once, which is why it had previously seemed to have no effect. TAA sharpens twice — once as a post pass at 0.5 and again on the history it samples at 0.35, both on by default — and FSR ignores both and does its own. Turning down only the obvious one leaves the image still crunchy.

The curve is anchored at the four levels the earlier cycler had, so anything already tuned to Low or Medium is byte-identical; the slider only fills in between. It is piecewise rather than one interpolation because the anchors are not evenly spaced — the post pass doubles between Medium and High while the history pass barely moves.

The default is Low, not Medium. Medium reproduces HDRP's stock values, and HDRP's stock values are the two passes stacked — which is the over-sharpened look the control exists to fix.

Dynamic resolution

Enabled in the pipeline asset from the very beginning, and it never moved a pixel. The scaler handed to HDRP returned a fixed number, so the machinery ran every frame and always got the same answer back — and the camera flag that lets any of it apply was only set when an upscaler was on. Enabled everywhere, doing nothing.

It is one row rather than a toggle beside a target, because a target that is switched off is a control that does nothing: Dynamic Resolution: Target 120 FPS says both things. The controller drops fast and climbs slowly on purpose — being slow is what the player feels now, while climbing back eagerly is what makes these systems visibly pump when a scene is briefly cheap.

It is a pure class with no UnityEngine dependency, so a thousand simulated frames run in a millisecond. That matters more here than elsewhere: a controller that hunts by two percent forever passes any code review and is maddening on screen.

Two HDRP limits worth knowing before designing this screen again

Render scale can never exceed 100%. DynamicResolutionHandler.ApplyScalesOnSize clamps with Math.Min(scaledSize, size) below the hardware/software branch, so it binds on both paths. That maxPercentage accepts values up to 300%, and that the RTHandle system would happily grow to fit, are both red herrings. Supersampling would need a different mechanism entirely.

The min and max percentages are asset-only. They are the one thing here that would have to be written back to the pipeline asset, and DLSS and FSR2 overwrite them from their own optimal settings the moment either is active. Cutting the row that edited them was right; cutting the feature along with it was not, and dynamic resolution went unbuilt for far longer than it needed to as a result. The 50–100% band the asset already defines was always exactly the range a target-frame-rate control wanted.

Render scale reaches HDRP through SetDynamicResScaler in the User slot. The earlier code called ScalableBufferManager.ResizeBuffers directly, which HDRP overwrites from the dynamic resolution handler every frame — so the row appeared to work and changed nothing that survived. The upscalers claim the System slot while they are active and HDRP reselects User at the top of each camera, which is what makes the row apply exactly when it claims to.

Controls that admit what they cannot do

Every row that would otherwise sit there inert says why: "Ignored while VSync is on" under the frame cap, "This GPU has no ray tracing support" on hardware without DXR, "Set by the upscaler" on render scale, "Replaced by FSR" on anti-aliasing, "Ray traced levels need a DXR GPU" where a ladder stops at High, "Dynamic shadows are off at this level" on the quality row itself. Three separate dead controls turned up in this project — a volume slider with no listeners, a quality dropdown backed by one asset, an attack-speed upgrade that never applied. This is the habit that came out of them.

A note was not enough on its own. An unavailable row still looked exactly like a working one and simply swallowed the click, which is the same failure in a quieter register. Rows now dim and refuse the click — including when a row is down to a single option, which is how the ray-traced rungs vanishing on a non-DXR machine can leave one with nothing to choose.

That took three pieces, because the obvious one did nothing. GraphicsOption dims its label and value and clears interactable on both steppers — but these buttons are built with Transition.None, so interactable blocks the click and changes not one pixel. HoloButtonHighlight owns their visual language, so the dimming went there, along with refusing to highlight and declining both the hover and click sounds. A disabled Selectable still delivers pointer events to the other handlers on the object, so without that last check a dead stepper played a click sound for a click that did nothing — worse than silence, because it claims something happened.

The greying immediately caught one

The Upscaling row went permanently grey, and the cause was not the greying. Every preset shipped with an empty advancedUpscalerNames, inherited from all three stock bases. HDRP only walks the upscalers named there, and the director checks that list before offering the row — precisely so it never presents a control that cannot work. With the list empty that check did its job too well: FSR2 is detected on this hardware and the row still had nothing but Off, and had done since the presets were first built.

The two checks answer different questions, which is why it stayed hidden. The hardware flag says what is present; the asset list says what is permitted. Only the intersection can be offered, and only one of them was filled in.

VSync, and the frame cap that replaced it

A crash and two-second stalls, on one machine, only with VSync on. The cause turned out to be arithmetic rather than a bug: a 200 Hz display is a 5 ms refresh interval, and the game renders a frame in 4.3–5.0 ms. Every single frame was a coin flip on whether it made the vblank, and the driver answered that by hanging for nearly two seconds at a time.

The fix cannot be "cap the frame rate and keep VSync": Unity ignores targetFrameRate entirely while vSyncCount is non-zero, so the two cannot be combined however much one would like to sit just below refresh and sync. The rows say so rather than letting one silently defeat the other.

So the frame cap gained a Just under display option, derived from whichever monitor the game is on rather than typed — a fixed 144 is the boundary on a 144 Hz panel and nowhere near it on a 165 Hz one. Its margin is a proportion, about 4%, because a flat two frames is 3.3% at 60 Hz and 1% at 200 Hz, where the whole interval is 5 ms and that margin buys nothing at all.

A number derived once is a number that goes stale

Unity's own documentation warns not to assume the refresh rate seen at startup persists: monitors change when a window moves between displays, laptops throttle when unplugged. The derived cap was computed only when a setting changed, never when the display did — so dragging the game to a second monitor would have kept capping to the first one's refresh rate. It is now re-derived when the display moves underneath it.

Separately, vSyncCount was stored per quality level as well as by the player's setting — Medium, High and Very High each turned VSync on independently. The director re-asserted after every quality change so it won in practice, but that is the same value in two places, and all three levels are now zero.

The interface also has a real typeface now. Chakra Petch, found by searching the font folder rather than by a hardcoded path — seven of those broke silently in the reorganisation, and they only fail at the moment somebody runs a tool.

What drives the editor

The project carries com.unity.pipeline, which runs an HTTP server inside the editor so Unity's CLI can drive it from a terminal: create assets, run C# against the live domain, enter play mode, capture the game view. It replaced com.unity.ai.assistant, whose relay did a narrower version of the same job and refused several things outright — refreshing the AssetDatabase, deleting an asset, and running C# without wrapping it in a namespace of its own.

The difference that mattered was recompilation. The old relay would not trigger a domain reload, because the reload severed its own connection, so every new script needed the editor window focused by hand before it existed. The pipeline drops its connection mid-reload and reconnects on the far side, which closes the loop: write a script, compile it, attach it, and confirm the type is live in the loaded domain without touching the editor.

It also made the captions visible for the first time. Capturing the game view with the composited backbuffer includes Screen Space Overlay canvases, which is where they live — before that they had been diagnosed by reading vertex counts, because the relay's camera capture rendered through a camera and missed overlay UI entirely.

A package that edits your player settings

BasePipelineServer.Start() sets Application.runInBackground = true every time it starts — every editor launch, every domain reload — so the editor keeps pumping its update loop while unfocused and can go on answering commands. In the editor that assignment writes through to PlayerSettings, so setting it back by hand lasts exactly until the next launch.

Nothing in a build asks for it: the runtime half of the pipeline is opt-in through a config asset this project does not have, and should not gain. But PlayerSettings is baked into builds, and this game has no pause — left on, alt-tabbing does not stop the run, and the player returns to a death they were not present for. RunInBackgroundOff is an IPreprocessBuildWithReport that clears the flag as a build starts, which is the only place it can be won.

The engine version, and what 6.6 moved

The project runs on Unity 6.6 (6000.6.0f1) and HDRP 17.6. The renderer did not move with it: HDRP’s 17.6 changelog records only that its version rose to match a related graphics package, so this was an editor and tooling upgrade rather than a rendering one.

Five packages left the manifest first, each checked rather than assumed — Entities and Entities Graphics, against a project with no ECS types, systems or bakers anywhere in it; Timeline, against no PlayableDirector in any script, scene or prefab and no .playable asset; AI Navigation, against no NavMesh of any kind, since the enemies chase by orbit arithmetic rather than by pathfinding; and Multiplayer Center, against a single-player game. Eight entries left the lock, because Serialization, Scriptable Build Pipeline and Profiling Core had come in behind Entities — and Serialization is deprecated in 6.6, so it would have needed answering for regardless.

Collections and Burst look just as unused and cannot go: Render Pipelines Core depends on both, so they are HDRP’s rather than the project’s, and Burst’s 2.0 major arrives with the engine whatever the manifest says.

The switch that decides what ships moved somewhere you cannot see it

6.6 splits the old Development Build checkbox in two, because its managed half was never reliable — C# compiles once and is reused across different native binaries, so classifying it at build time was guesswork. The box still picks the player; a Managed Code Variant dropdown in Player Settings now decides which symbols reach C#, across four levels — Debug, Checked, Instrumented, Release — and it defaults to Release, which defines none of them. DEVELOPMENT_BUILD and UNITY_64 are deprecated alongside it, warning as UAC0009 and UAC0008, and stop being emitted in 6.8.

Both of this project’s uses are gone. DebugMenu gates on UNITY_INCLUDE_INSTRUMENTATION now, and SystemProfile dropped its #if for a runtime Debug.isDebugBuild — which is what it should always have been, since it only prints a label into a diagnostic banner.

The variant is set to Checked, so the debug menu compiles into every build — including one with Development Build unticked. That is the reverse of the old arrangement, where an unticked box kept it out, and this is the menu that hands out levels and invulnerability. Set the variant to Release before a build goes to anybody else. The same dropdown governs HDRP’s debug overlays, the rendering debugger and physics integrity checks, so a development build with it left at Release is missing all of them — which reads as a broken install rather than as a setting.

Two things the upgrade settled

com.unity.pipeline was the real risk in moving. It is experimental, it declares "unity": "6000.0", and it is what the terminal drives the editor through — so losing it would have cost the whole loop described above. It came through unchanged.

And the fault where a Player build nulled all six probe-volume references in Game Baking Set.asset did not reproduce. A confirmed clean build — the editor log says “Rebuilding Data files because BuildOptions.CleanBuildCache is set” — left the asset untouched, its modification time still predating the build, and the references at six resolved and none null, through that build and an editor restart afterwards. Two explanations died there: that Editor builds broke it while CLI builds did not, which was a false correlation drawn from three samples in which the CLI build had merely been incremental; and that clean builds were the trigger. The streaming conversion demonstrably ran, since APVStreamingAssets shipped into the player, so “the conversion ran” was never sufficient to cause the rewrite. Worth checking after a build for a while yet before trusting it.

A pool that hands the same object to two callers, a benchmark figure that misrepresents a tester's machine, a health bar showing a red loss stretch while the player is healing, a volume slider that does nothing over its bottom half, an upscaler handed the opposite quality mode to the one the player picked — none of those announce themselves.

Part IV

Ideas worth carrying forward

Read the data, don't retype it

Every migration — waves, enemies, the boss, the sky — was done by a tool that read the existing values and wrote the new form. None of it was transcribed by hand. That's why 21 spawners and 32 muzzle references transferred without a single typo.

Separate the rule from the Unity object

HealthState, SkillPool, SpawnMath, VolleyTimer, ShipMotion, ArenaGeometry, and later BarMotion, FrameTimeStats, AudioLevels and DisplayOptions — none of them are MonoBehaviours. That's what made 264 tests possible, and it's the single most repeatable idea here.

Put a seam where a swap is coming

The input facade was built before the package existed. When it arrived, the change was one class. The same shape would work for save systems, audio, or analytics.

Derive the number, don't store it twice

The countdown to the boss and the boss's actual spawn time were two independent values that had to agree, and they had drifted to 60 and 300 — the scene carried two Timer components, one of which called showHpBar() on a null reference every frame from a minute in. The surviving timer now reads its length from the wave asset's boss stream, located by the prefab carrying BossEmitter rather than by label, so retuning the spawn moves the bar with it. A value stored twice is a value that will eventually disagree.

A repair can erase the evidence a later one needs

An early pass filled in every unwired bossHpBar reference. That looked like tidying. It also destroyed the only signal distinguishing the correctly configured timer from the broken one, so the consolidation step written afterwards confidently picked the wrong one. Patching a symptom can remove the information required to find the cause — worth remembering before "fixing" something not yet understood.

A setting that does nothing looks exactly like one that works

Three separate controls in this project were enabled, wired, and inert. Dynamic resolution ran its machinery every frame against a scaler that returned a constant. The upscaling row offered FSR after it had been taken out of the pipeline asset, because availability was checked against the hardware rather than against what the asset actually lists. A sharpness control moved one of the two passes TAA runs, leaving the image visibly unchanged.

None of them threw, logged, or looked wrong in code review. What catches this class of fault is asking, for every setting, what would be different on screen if this were doing nothing at all — and if the answer is "nothing", finding out why before shipping it. The note line under each row exists for the cases where the honest answer is that it genuinely does nothing right now.

An index is not an identity

The menu builder set each row's setting with SerializedProperty.enumValueIndex, which is the value's position in the enum declaration rather than the value itself. That worked for as long as the enum ran 0 to 11 with no gaps. Removing the old combined upscaling row left a hole at 11, and every row after it silently drove the wrong setting — the row labelled Anti-Aliasing was writing the quality preset — while the last one threw.

The property that means what it says is intValue. The same call in the audio rows was equally wrong and equally invisible, because AudioChannel happens to be contiguous. Two representations that agree by coincidence will keep agreeing right up until they matter.

A poisoned setting outlives the bug that wrote it

While those rows were mis-wired, cycling one wrote quality level 0 into PlayerPrefs. Fixing the rows did not undo it — preferences survive rebuilds and play sessions — and level 0 was the tier that crashed HDRP — the maxShadowRequests = 0 fault written up under Quality presets and settings — so the game stayed unlaunchable after the actual defect was gone. Worth asking, after any bug in code that persists something: what did it write while it was broken, and is that still there?

Read the live state, not the last saved one

Three rounds were spent on silent music. The scene files were read from disk while the editor held unsaved changes, and the conclusion drawn from them — "the clip is definitively not assigned" — described a state that no longer existed and contradicted what was visible in the Inspector. The asterisk in the window title was the tell, and it was there the whole time. When a tool and a person disagree about what is on screen, the person is looking at the live thing.

It recurred while building the Display screen: the pipeline asset was read from disk and reported an upscaler priority order that had already been changed in the Inspector. The reliable answer is to ask the editor itself — running a few lines of C# inside it returns SystemInfo, live asset state and detection flags as they actually are. That is also how the graphics card was identified and how the shadow crash was pinned to a specific quality tier, in minutes rather than by inference.

Preserve behaviour, flag the judgement

The boss's 2 EXP, the laser's fire rate, the 301-second cutoff, the "SexTUPLO Shot!" banner — all preserved exactly, all surfaced as things to decide. Three of those four have since been decided, which is the point: they were reachable as one field each when the moment came. Migration and rebalancing are different jobs, and mixing them makes both harder to review.

What's still open

Decisions, not bugs

  • Whether the eighteen 2023 jam branches still on the remote are kept. They are stale, but they are also the only record of who did what on the original project.

Open on the current front

  • The cloud bank is committed switched off. Arena Cloud Bank has m_IsActive: 0 in the scene. It was disabled two commits before the sparsity work to keep it out of a lightmap bake and has not been switched back on, so the mask that was just retuned is not being rendered by anything. The volume also grew to 2000 × 300 × 2000 in the same commit, which stretches one mask tile to 1000 world units — worth a look with fresh eyes before it goes back on.
  • The shadow work is cut; the millisecond is still unattributed. Bullet-light shadows went from five casters to one per volley, measured at sixty per cent less shadow geometry and half the draw calls. What remains is the confirmation: that measurement is submitted work from a paused editor frame with GPU timing unavailable, so it proves the mechanism was large without proving it was the 8.4 ms spike. A capture from a real run closes it.
  • The shadow budget now bites at the other end of the run. shadowCastingCount is 4, which costs nothing once Shot Upgrade lands — only two volleys are lit — but means four casters in the opening minute, when every bullet is its own volley and there is least else on screen to justify it. 2 is the defensible number; 4 is what is in the scene.
  • The wreckage reads only as a silhouette. The plates carry the boss's own hull material, which is nearly black; against the sky or the lava they are unmistakable, and against the dark island one can be lost. An emissive tint would fix it and would also be the first thing in the arena that glows because it is dangerous rather than because it is hot — a call about the art direction rather than about the mechanic, so it has deliberately not been made.
  • The boss's second act has been measured but not played. Every figure above — nine plates, one forced move every four seconds, 36.5 seconds of standing still — comes from a probe with the player parked and the arena controlled. Standing still is the worst case and nobody plays that way. The cadence, the lane response and the plate's life are one serialized field each for exactly that reason.
  • Overlapping offers stack their captions. Levelling again while an offer is still on the ring puts a second set out rather than replacing the first, which is deliberate — replacing it would quietly delete an upgrade the player had earned. Two pickups near the same bearing now stack two labels on top of each other, which was invisible when they were coloured shapes. Doubling the run made it likelier rather than rarer: a run reaches level twenty-one where it used to reach nine, so there are more than twice as many level-ups in play.
  • Max Health is optional now in a way it was not. One guaranteed +20 became four +5s. The ceiling is the same for a player who takes all four, but taking one or two ends a run lower than the old single pick did. Whether that reads as a meaningful choice or as a nerf is a question only playing answers.
  • Ray-traced reflections are validated; the rest of the rungs are not. RT Reflections was selected in a build on DXR hardware and visibly changed the image — which is precisely the bar ray-traced shadows failed. That row shipped allocating a screen-space buffer no light wrote to, invisible in the editor and haze in a build, and was removed outright. RT global illumination is reachable and deliberately unused for the reasons above; no tier selects a ray-traced rung by default, and compiling ray tracing into three of the four tiers makes every build larger.
  • Enemy reuse has only been lightly exercised. Pooling defects cannot appear until the warmup is exhausted and instances start recycling, which takes a few minutes of play. The three failure modes to watch for are enemies dying to one bullet regardless of type, an enemy setting off the wrong way round the ring, and Enemy_1 firing faster as a run goes on.
  • LFS is no longer the constraint on lighting. It was: a bake went through LFS against a 1 GB free quota at roughly 40 MB a time, which is a couple of dozen commits before the quota is spent. The bake output is gitignored now — the lightmap EXR, its directionality and shadowmask maps, and the probe volume cell data — and nothing that produces it is: the Baking Set, the Lighting Settings, the volume profiles and the scene itself all stay tracked, so a fresh clone reproduces it with Generate Lighting. Checked rather than assumed: zero lightmap or cell-data files are in LFS today, against 273 tracked files in total. The cost of a bake is now disk and time, not quota.
  • The bake was turned down, then turned back up past where it started. Iterating on lighting is slow, so the settings were halved — 2048 lightmaps, two bounces, half the samples. Once the quota argument above went away they went the other way instead: 4096 lightmaps, uncompressed, bake resolution 50, four bounces, and the light-probe sample multiplier back to 8. Sample counts are the one thing still at the reduced figures (32 direct, 512 indirect, 256 environment), which is the obvious next thing to raise if a bake still looks noisy. The current output is 68 MB on disk and costs nothing to keep.

The bullet hell direction was explored and shelved. The profile can afford it — 1500 simultaneous bullets measured at 0.056 ms, around 0.3% of a frame — and the design work is recorded in the history, but the decision was to improve what exists rather than add a mode. It is available to pick up rather than abandoned.

Housekeeping

  • Prefabs/VFX/Explosion.prefab and PlayerHit.prefab are orphaned outright now that _Archive~ has gone with it the last reference to either. PlayerHit is the one that was wearing TESTE cenario_2.mat, a scenery test material, which is worth knowing before anything reuses it.
  • The old HUD art in Art/Textures is no longer drawn — the shaders replaced all of it — but saying it is referenced by nothing was wrong, and worth correcting because it is the kind of claim that gets a live asset deleted. Unity's dependency graph puts hpBar.png and TESTE 1 hud 4copy.png on Image components that are active and enabled, on two root objects both named Border. They render nothing only because neither has a Canvas anywhere above it, which is a condition of the scene rather than of the files: reparent either one and the old art is back on screen. Delete the objects before the textures, or the references dangle. skillSlot, the four button sprites, the menu background and the PUC logo are genuinely at zero. timeBar has been deleted; the rest are still there.
  • StarfieldCubemapBaker can no longer run: its six source textures were deleted once the cross was baked. That is fine unless the sky ever needs re-baking, in which case they have to come back first.
  • Git history still carries the 302 MB of deleted sky textures; only a history rewrite removes them.

Four of these have since been cleared, each confirmed dead rather than assumed: com.unity.visualscripting (no code reference anywhere under Assets, and nothing in packages-lock.json depending on it), VolumeBar.mat (zero inbound references), timeBar.png (one reference, from inside the archive), and Assets/_Archive~ itself — 950 KB the editor had never loaded. Removing the archive is what cleared timeBar's last reference, so nothing is left pointing at anything that has gone.

Settled: the settings menus

Audio, Display and Graphics are built and tested. Three things about them are decisions rather than gaps, and all three will look like omissions to anyone reading the screen cold:

  • No min/max row beside Dynamic Resolution. The band itself is asset-only and both upscalers overwrite it, so the control chases a target frame rate within the asset's 50–100% instead.
  • No render scale above 100%. HDRP clamps it; supersampling is a different feature, not a setting.
  • No FSR entry beside DLAA in the anti-aliasing list. Unity's FSR2 binding has no native-resolution mode.
One path that has never actually executed

The development machine is a Radeon RX 6700 XT, and DLSSPass.SetupFeature requires the graphics device vendor string to contain "nvidia" — this one reports "ATI". DLSS therefore cannot initialise here, the DLSS and DLAA rows are correctly hidden, and those code paths have never run. They are verified against the HDRP package source and the quality mapping is unit-tested, but the first real execution will be on someone else's machine. Do not read the missing rows as a bug.

Settled: the pipeline

HDRP is the project. hdrp-experiment was promoted to main and deleted, and because it had only ever been ahead of main rather than divergent, that was a fast-forward — no merge, no force-push, and git branch -d accepted the delete, which is its own proof nothing was stranded.

Why the editor never noticed

The obvious sequence — check out main, then merge — would have rewound the working tree 49 commits and replayed it, with Unity watching hundreds of assets vanish and return. Moving the ref instead (git branch -f main hdrp-experiment) leaves both names on the same commit, so the checkout that follows changes zero files. The project stayed open throughout.

The branch-locked caveat is now moot: HdrpVfxMaterialFixup, LavaLightPlacer and the render-pipeline references in SurvivalChaos.Editor.asmdef have nowhere else they need to go. That asmdef now names three: HighDefinition.Runtime, Core.Runtime for the dynamic-resolution and probe-volume enums, and GPUDriven.Runtime for GPUResidentDrawerMode. Each was added only when a preset field genuinely needed the type — the first attempt to reach one of them failed to compile, which is a cheaper way to find out than shipping.
